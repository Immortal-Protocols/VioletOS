# Bootloader

The handset bootloader loads the boot image. The [VioletOS loader](loader.c) checks the handoff, prepares memory and starts seL4, which launches the first user process. Use `make qemu-image` or `make moto` to build the corresponding image.

**AArch64.** `make moto64` builds the handset loader for AArch64: [loader64.S](loader64.S) (an arm64 Image that LK starts at EL2; it drops to EL1, then runs the same [loader.c](loader.c) checks and staging, and a trampoline turns the MMU on and enters the 64-bit kernel) linked by [loader64.ld](loader64.ld) at 0x40080000. Its boot history stages are 21-23, and a refused handoff is recorded as stage 40 + the failed check ([targets/moto-g-pure](../../targets/moto-g-pure/README.md#aarch64-boot-path)).

**Verified boot, QEMU only.** The QEMU loader starts the kernel and the root task only if they match a boot manifest signed by a key the image pins, and only if the system is not older than the bootloader's stored rollback floor ([verified.rs](verified.rs); the manifest comes from [tools/boot_manifest.py](../../tools/boot_manifest.py)). A release image's manifest also binds the open apps' image. Otherwise it prints `VioletOS loader: boot refused, reason N` and stops before copying anything. `make test-unit` runs [test_verified.sh](test_verified.sh).

**AArch64.** The qemu64 system image runs the same check from its entry stub ([targets/qemu64/verify.c](../../targets/qemu64/verify.c)), with the same floor. The AArch64 handset loader (`make moto64`) runs `verified()` too, for a manifest signed for `MOTO` (built by `targets/moto-g-pure/build64.py` for the kernel the loader carries): a refusal paints the red band and records boot stage 90 + the reason. LK keeps no rollback floor, so the handset check has none (version 0 is still refused). On the phone (November 28, 2026) the image as built started and reported `verified_boot_version` 1 over USB (`moto-debug`), and the same image with one kernel byte changed was refused on each of B's seven tries: the 32-bit VioletOS LK then started from slot A reported `previous_boot_stage` 97 (90 + reason 7). Its unlocked bootloader means it proves nothing about a replaced image (below).

**The AArch32 handset loader checks no signature.** The phone's bootloader is unlocked and starts whatever boot image is written to it, so a check inside that image would not stop a replaced image. [docs/verified-boot.md](../../docs/verified-boot.md) has the whole chain, the refusal reasons, and what a locked handset would need.
