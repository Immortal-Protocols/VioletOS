# Open Runtime

The phone's apps are open apps, written in Rust: **Home**, **Settings**, **Ladybird Browser**, **Bitchat**, **Violet Agent** and **Locomo Music** ([apps/open](../../apps/open), sharing the [violet](../../apps/lib/violet) crate for the devices, drawing, text and HTTPS with rustls). Music streams the *Glass Orchard* album from the Rose Music library over HTTPS, decodes its MP3s itself (symphonia) and plays 48 kHz PCM through `/dev/violet/audio`, with a full-resolution player drawn into `/dev/violet/screen`. Home fetches the time from wttr.in itself; no URL, decoder or playback state lives in an OS service. Home is the main screen on both targets; the phone's settings are in the Settings app.

The Open Runtime runs ordinary Linux ARM programs on VioletOS, with no Linux kernel anywhere. A static binary built for `armv7-unknown-linux-musleabihf`, a Go program built with `GOOS=linux GOARCH=arm GOARM=7`, or a Python script with a `#!/bin/python3` line goes into `/apps` and runs as it is. It implements the [open app model RFC](../../docs/open-app-model-rfc.md).

## Try it

Run `make emulator`: it boots to Home, which shows an icon for each titled app (one with an `app.txt`, or one the agent installed); tapping one runs it. `apps` in `/dev/violet/sys` shows a plain list of every program in `/apps`. Programs that print go to the Open Runtime's log. In QEMU the log is a page of guest memory at `0x49220000`; on the handset, `build/moto-package open-log` prints it, and `build/moto-package open-run=/apps/NAME` starts a program over USB.

On the handset, `build/moto-package open-push=NAME < FILE` installs a program into `/apps` over USB without a reboot (about 400 KB/s; it lasts until the next restart), so the phone keeps its Wi-Fi connection while you iterate. `open-run` of a program that is already running replaces it.

`make test-open-apps` drives the built-in apps: Stopwatch keeps its time in `/data` across a restart, Sounds plays the chime, and Weather fetches live conditions (skipped offline).

`make test-open` starts each test program and checks its output, the frames drawn through `/dev/violet/screen`, taps, the PCM it plays and the trip to Home and back.

## Building programs for /apps

[tools/build_initfs.py](../../tools/build_initfs.py) builds the image from `apps/open`. Each folder becomes `/apps/NAME`:

- `Cargo.toml`: a member of the Cargo workspace in [apps/Cargo.toml](../../apps/Cargo.toml), built with crates for `armv7-unknown-linux-musleabihf` (ring, under rustls, compiles a little C with the NDK's clang).
- `main.rs`: built as a static Rust `std` program with `rustc` alone. Needs `rustup target add armv7-unknown-linux-musleabihf`.
- `main.go`: built with Go for `linux/arm`, `GOARM=7`, `CGO_ENABLED=0`.
- `main.c`: built against musl with the NDK's clang. Build the musl sysroot once with `python3 tools/build_python.py musl`.
- An `app.txt` names the app; titled apps come first in the list. The handset image leaves out Python and the network test programs (`HANDSET_SKIP`) to fit its boot partition.
- Anything else is copied as it is. A file starting with `#!` runs under the named interpreter; a `.py` file without one runs under `/bin/python3`; a folder runs its `main` or `main.py`.

`python3 tools/build_python.py python` cross-builds CPython 3.12 statically against musl (with zlib) and the image picks it up as `/bin/python3` and `/lib/python3.12`. It needs Homebrew's `python@3.12` on the Mac. Downloads are pinned by SHA-256.

QEMU loads the image uncompressed at `0x4a000000`. The handset carries it gzip-compressed as its boot image's ramdisk, where the stock Android ramdisk used to be; the loader copies it to `0xc0000000` and the Open Runtime unpacks it at start (about 3 seconds for 20 MB on the phone).

## How it works

```
 app thread ── svc #0 (Linux syscall in r7) ──► seL4: unknown syscall ──► fault endpoint
                                                                             │
 Open Runtime (component 24) ◄──────────────────────────────────────────────┘
   syscall.rs: Linux ARM EABI calls       device.rs: /dev/violet/{screen,events,sys,audio,camera}, hci.rs: /dev/violet/hci
   procmgr.rs: address spaces, ELF        fs.rs: /apps image + writable in-memory layer
   pool.rs: physical pages for apps       Runtime client 9: focus, touch, Home
```

- **Processes.** The supervisor gives the Open Runtime its own CSpace (16K slots), page directory, the ASID pool, 8 MiB of kernel memory (4 MiB on a phone without a spare 8 MiB block) and a pool of physical memory (384 MiB in QEMU, 256 MiB on the handset). The Open Runtime makes each app's page directory, CNode and threads itself and is their fault handler, so an app's crash ends that app and nothing else.
- **System calls.** seL4's system calls use negative numbers in `r7`; Linux's are positive, so a Linux `svc #0` reaches the Open Runtime as an unknown-syscall fault carrying `r0`–`r7`. The reply sets `r0` and moves the restart address past the `svc`. Calls that must wait (futexes, `read` of events, `poll`, `epoll_wait`, `nanosleep`, a full audio ring) keep the thread's reply capability and answer later. About 150 calls are handled; [syscall.rs](syscall.rs) lists them.
- **Memory.** Pages are 64 KiB, mapped on first touch. Regions still start on any 4 KiB boundary, as Linux allows. `mmap`, `munmap`, `mprotect` and `brk` maintain the regions; every pool page stays mapped in the Open Runtime as well, so reading app memory is a plain load.
- **Memory protection** ([vma.rs](vma.rs), [procmgr.rs](../../system/supervisor/procmgr.rs), [entropy.rs](entropy.rs); host tests in [tests/memprot_host.rs](tests/memprot_host.rs), `make test-wx` in QEMU).
  - *Hardware rights.* An app's mapping of a page follows its regions: read-only, read-write or read-execute, from the ELF segment flags and from `mmap`/`mprotect`. Every mapping that is not code is Execute-Never, the stack included; code and constants are read-only. No page is ever writable and executable. `PROT_NONE` memory is unmapped and keeps its contents. A write to read-only memory, a jump into data, or any access outside a region ends the app (status 139; the log names the access).
  - *W^X policy.* Executable memory comes only from the program loader. `mmap` and `mprotect` answer `EACCES` to `PROT_EXEC` on anything that is not already code, to `PROT_WRITE|PROT_EXEC`, and to anything that would put a region that is not code (writable, read-only or `PROT_NONE`, anonymous or a file) in a 64 KiB page that holds code: the hardware runs whole pages, so a page of code holds only what the loader put there. The loader refuses a program with a writable and executable segment, or with code sharing a 64 KiB page with any other segment (constants included; `tools/elf_check.py` says so at build time). It cannot see constants a linker merged into the code segment itself. The trampoline page is the runtime's: `munmap` over it is `EINVAL`, `mmap` and `mprotect` `EACCES`, and each new thread's trampoline is written only after the page is looked up and found unchanged. Nothing shipped needs more: the Rust, C, Go and Python programs and Ladybird (which runs no scripts) never ask for executable memory. A JIT, `dlopen` or libffi closures would get `EACCES`; there is no per-app exception yet. Violet Shield still sees the W+X attempt first.
  - *System calls.* The runtime copies to and from app memory only where the app itself may write or read, checked against the regions at 4 KiB precision: `read(fd, code_address, n)` is `EFAULT`, not a patch. Only the loader and the file contents of an `mmap` are written with the runtime's own authority, and file contents never into a page that holds code. `getrandom` checks its whole buffer before writing any of it.
  - *The runtime's own view* of app memory (and its heap) is mapped Execute-Never, so nothing an app wrote can run inside the Open Runtime.
  - *Layout.* Each start draws a new layout: the PIE load address (12 bits of 64 KiB steps), the top of the `mmap` area (12 bits), the stack (11 bits, plus 8 bits of 16-byte padding), the gap before the heap (8 bits) and the trampoline page (1 of 224). `AT_RANDOM` is 16 fresh bytes.
  - *Random numbers.* `getrandom`, `/dev/urandom`, `AT_RANDOM` and the layout come from one HMAC_DRBG (SHA-256). It is seeded at start from timer jitter: the counter is sampled after each yield to the other processes until a deliberately low estimate credits the samples with 256 bits, or 32768 samples are taken. A sample counts (as half a bit) only if its step differs by two ticks or more from each of the eight steps before it, so a stuck or regular timer, a short repeating pattern, a slow drift and one tick of rounding count for nothing. Without that credit, or if the SHA-256 it uses fails its known answer, the generator stays unseeded: no app starts (each start tries again) and `getrandom` returns `EIO`. Every system call's arrival time is mixed in afterwards.
  - *Limits.* The hardware page is 64 KiB, so a `PROT_NONE` or read-only 4 KiB range that shares a page with writable memory is enforced for system calls and first touch but not against the app's own loads and stores (thread-stack guard pages are the common case). Every shipped program is linked at a fixed address (`ET_EXEC`), so its code does not move; `tools/build_initfs.py` lists them at build time, and `VIOLET_OPEN_PIE=1` links the Rust apps as static PIE (untested on the emulator and the phone). The random generator has no hardware source yet: the handset's secure-monitor generator is served only to Radio, and `Drbg::reseed` is the hook for it. Timer jitter is not a validated entropy source: the estimate assumes steps that are independent of each other, which a longer hidden pattern would not be, and on a quiet handset it may find too little and keep apps from starting until the hardware source is wired.
- **Threads.** `clone` makes an seL4 thread in the same address space. The thread pointer is `TPIDRURO`, as on Linux; the kernel is built with `KernelArmTLSReg=tpidruro` and the Open Runtime sets it with `seL4_TCB_SetTLSBase`. seL4 clears the Thumb bit whenever registers are written, so new threads start at a one-instruction ARM trampoline (`ldr pc, [pc, #-4]`) that jumps to the Thumb or ARM target.
- **Signals** ([signal.rs](signal.rs) holds the rules, the delivery is at the end of [syscall.rs](syscall.rs); host tests in [tests/abi_host.rs](tests/abi_host.rs), `make test-abi` in QEMU). `rt_sigaction` (`SA_SIGINFO`, `SA_ONSTACK`, `SA_RESTART`, `SA_NODEFER`, `SA_RESETHAND`), `rt_sigprocmask`, `rt_sigpending`, `sigaltstack`, `rt_sigsuspend`, `pause`, `rt_sigtimedwait`, `rt_sigreturn`, `kill`, `tkill`, `tgkill` and `rt_(tg)sigqueueinfo`. A handler gets a Linux ARM `rt_sigframe` (siginfo, a ucontext with the VFP block) on its stack or its alternate stack. It runs through the *signal gate*, ARM code at the end of the trampoline page: it stores r8-r12 and d0-d31/FPSCR into the frame (seL4 lets the runtime write a thread's core registers but not its VFP ones), calls the handler, loads them back from the frame and calls `rt_sigreturn`; the libc's `sa_restorer` is not used. A thread takes a signal when one of its calls is answered; a thread blocked in a call is interrupted at once (`EINTR`, or the call restarts under `SA_RESTART` where Linux restarts it); a thread running in user code is suspended and redirected, but only after the runtime has drained its fault queue, on one core and without MCS (so no queued fault is lost to the suspend), and not inside a Thumb IT block or with the GE flags set (a register write would lose them, so it tries again 1 ms later). Thumb code resumes through the thread's trampoline. Under MCS or with more cores, a running thread takes its signal at its next system call. A fault (`SIGSEGV` with `SEGV_MAPERR` or `SEGV_ACCERR` and `si_addr`, `SIGBUS` with `BUS_ADRALN` for an unaligned access or `BUS_ADRERR` for an allowed access the hardware still refuses, `SIGILL`) goes to a handler if the app has one and does not block it; otherwise the app ends as before (status 139 or 132) and its parent's wait status says which signal. A handler that keeps returning to the same fault is stopped after 256 faults with no system call but `rt_sigreturn` between them. Timers: `setitimer(ITIMER_REAL)` (and so `alarm`), `getitimer`, `timer_create` (`SIGEV_SIGNAL`, `SIGEV_NONE`, `SIGEV_THREAD_ID`) on the real-time and monotonic clocks (`TIMER_ABSTIME` on the timer's own clock); periods and first expiries are at least 1 ms, so no timer keeps the runtime (which runs above every app) from sleeping. A Shield-frozen or lifecycle-frozen app keeps its signals pending (SIGKILL apart): none ends it or runs a handler until it runs again. A vfork child takes signals as its own process: one that blocks in a call is interrupted, SIGKILL and other fatal signals end it at once (its parent goes on), and a running one takes a handler like any thread. An app may signal itself and its own descendants only (`EPERM` otherwise). Not modelled: job control (a stop signal with its default action is discarded, `SIGCONT` does nothing), CPU-time timers (`ITIMER_VIRTUAL`, `ITIMER_PROF`, `CLOCK_*_CPUTIME_ID` are `EINVAL`), `signalfd`, core dumps.
- **Processes** ([syscall.rs](syscall.rs), [procmgr.rs](../../system/supervisor/procmgr.rs) `fork_into`). `fork` (and `clone` without `CLONE_VM`) copies the caller's memory into a new app slot: every page it owns, eagerly (there is no copy-on-write), with the caller's thread returning 0; the screen surface is not copied. The call goes round the *fork gate* first (the signal gate with a fork helper as its handler), which stores the caller's r8-r12, d0-d31 and FPSCR in a frame on its stack, so the child gets them too (a `clone` with a child stack, or a stack with no room for the frame, forks without them). A process may have 64 children, running or zombie: fork and vfork return `EAGAIN` until it reaps some. A thread that ended leaves its slot and kernel objects to the next one the app makes, so spawning in a loop does not run out. A process tree shares one socket quota and one resolver table: sockets.rs counts by `quota_owner`, the pid of the oldest running ancestor. A Violet Shield KillApp verdict ends every process of the owner (`end_family`). Violet Shield freezes act on a whole owner: while one process of an app is frozen, every call by its other processes (forks share the owner) waits, and is made again when none is. `vfork` and `clone(CLONE_VM|CLONE_VFORK)`, which musl's `posix_spawn`, Rust's `Command` and Go's `os/exec` use, run the child as a thread in the parent's memory with its own pid, descriptors, working directory and signal actions while the parent waits. `execve`/`execveat` check the file, its `#!` line and the interpreter it names (the same path rules as any file: a refused or private one is `ENOENT`), the ELF headers and where every segment of the program and its loader would go (the W^X and 64 KiB page rules, `elf::check`, the loader's own code), and Violet Shield, which sees the program that runs (the interpreter, then the script) and the arguments after `argv[0]`, never `argv[0]` itself, first, so a failed `execve` returns with the caller intact (only running out of memory can fail after); an interpreter written since boot is what Sentinel and the Shield hash; then the program starts from scratch in the caller's slot (a vfork child's in a free one) with fresh memory at a fresh random layout, the argv and envp given, the descriptors without `FD_CLOEXEC` (`O_CLOEXEC`, `F_SETFD`, `pipe2`, `dup3`, `SOCK_CLOEXEC`, `EFD_CLOEXEC`, `EPOLL_CLOEXEC`) and caught signals reset. `wait4` and `waitid` (`WNOHANG`, `WNOWAIT`) report exit status and the signal that ended a child; `SIGCHLD` is raised (none if the parent ignores it or sets `SA_NOCLDWAIT`); orphans have no parent; `getppid` is real. Every process takes an app slot and counts against the app limit; fork never closes another app to make room (`EAGAIN`, or `ENOMEM` without the pool room for the copy and 4 MiB), and neither does a vfork child's `execve` unless its app holds `system` (as `launch` needs). An in-place `execve` ends a vfork child another thread runs (killed; a zombie for the new program). Not done: copy-on-write, process groups and sessions beyond the caller's own pid, VFP state for a vfork child (it starts with zeroed d0-d31; it may only `execve` or `_exit`), a vfork child that blocks on a descriptor (`EAGAIN`).
- **Dynamic linking.** A program whose `PT_INTERP` names `/lib/ld-musl-armhf.so.1` is loaded with musl's dynamic loader (its `libc.so`) placed at a random address in the `mmap` area, `AT_BASE` set and the thread starting at the loader ([elf.rs](elf.rs) checks the headers; any other interpreter is refused). The loader is taken only from the system image, never from a file an app wrote there, and is checked by the same W^X rules. The image ships it when built with `VIOLET_OPEN_LDSO=1` (`make test-abi` does; tools/build_initfs.py builds it from the musl source); a folder in the apps with a file named `dynamic` is linked against it. `dlopen` of another library still fails: mapping its code would need executable memory from `mmap`, which the W^X policy refuses.
- **Screen and touch.** The Open Runtime is Runtime's client 9. The boot launcher hands it focus as soon as Runtime answers; it then draws the app in front (Home, unless another app is open) directly to the framebuffer. It samples touch every 4 ms and passes each change (down, a finger that moved, up) to the app in front. An up is reported where the finger was last seen down: a controller's release sample need not carry a position (QEMU's is 0, 0). An app's surface is two 720 × 1600 BGRA8888 buffers that the app maps with `mmap`; `write` of a `PresentRect` copies that rectangle to the screen. Holding the top edge for a second, or writing `home` to `/dev/violet/sys`, leaves the app running in the background.
- **Background apps and low memory** ([lifecycle.rs](lifecycle.rs)). An app is *foreground* (on screen), *visible* (behind, but Home, the agent, holding an audio stream, the microphone or Bluetooth, uploading or still connecting over TCP, or within 5 s of leaving the front), *cached* (behind with none of those; it still runs for 10 s) or *frozen* (its threads suspended, its memory kept; none of its waits is served and it wakes nothing). A frozen app runs no code: an answer that comes for a call it is blocked in (a child's exit, a timer's signal to `sigtimedwait`, a futex wake, the end of a Shield freeze) is held until it thaws (`Wait::Held`), and a call or page fault that reached the runtime as it froze is made again then (the thread is answered back onto its `svc` and suspended). A child process (fork, posix_spawn) takes its state from the app that started it: a child of the app in front or of Home keeps running and is never closed for another app; one of a cached app freezes with it. A frozen app runs again the moment it is back in front. Below 64 MiB free in the pool, background apps get `EVENT_LIFECYCLE` value 4 (low memory: free what you can) once and cached apps freeze at once; below 16 MiB the runtime closes a frozen or cached app each second, and a launch or a page fault that finds the pool empty closes apps on demand: frozen first, then cached, then Settings, then visible apps, least recently used first and an app with an audio stream last. Only a launch, or a fault by the app in front, Home, the agent or one of their children, may close Settings or a visible app; a fault by any other app closes only frozen and cached apps, then the app itself, so an app cannot make itself visible (an audio fd, a TCP send) and evict the user's apps. The app in front, Home, the agent and an app the Shield holds are never closed for another app; one whose own fault finds nothing to close (Home included) is closed itself. A closed app exits with status 137 and the log says why; opening it again starts it afresh. Below 4 MiB of free runtime heap, the app holding the most of it in pipe buffers (256 KiB or more, any state but the protected ones) is closed first, else a cached one. Pipes are bounded so one app cannot drain that heap: 64 KiB a pipe, one page a pipe once an app's pipes hold 512 KiB, nothing past 1 MiB (a blocking write waits, `writev` too; non-blocking is `EAGAIN`; writes up to 4 KiB go whole; `POLLOUT` follows); a write with no reader left is `EPIPE` (no `SIGPIPE`). Not bounded yet: other runtime-heap buffers (UDP and socket queues, file data in the heap's file store) and per-app pool pages (no per-app page cap; the killer enforces the app limit). How many apps may run at once is set at boot: as many 512 KiB kernel-memory slices as fit (twelve, or seven with 4 MiB) and as many as the pool holds with 32 MiB kept for the app in front and two screen buffers plus 2 MiB for each other app. `memory` in `/dev/violet/sys` reports the pool, the heap and the limit, then each app's pages, surface, page tables and state, the pressure level and the last apps closed, every app's only to an app with the `system` capability (and to `@sys memory` over USB) and the caller's own entry and the pressure to any other; names are printed with anything but letters, digits, `.`, `-` and `_` as `_`. Python apps see the low-memory event as `"lowmemory"` (the Rust crate as `Event::low_memory`); the pool refuses (and counts) a page given back while it is still free (a give-back after another app took the page again is not caught: pages carry no owner). `make test-lifecycle` (local) checks this in QEMU.
- **Frames** ([docs/8ms-frame-pipeline-rfc.md](../../docs/8ms-frame-pipeline-rfc.md)). Rust apps draw straight into the mapped surface (`Screen::canvas` in the violet crate), redraw only what changed and present just that rectangle. On the handset a present never tears: [scanout.rs](scanout.rs) reads the panel's scan line from the display engine and copies only while the panel is not reading those rows; otherwise the presenting thread waits (a full frame waits for the panel to near its last line, at most one frame). `ioctl(SCREEN_IOC_WAIT_VSYNC)` blocks until the next frame starts. In QEMU, presents tell the Mac viewer which rows changed, and it redraws at the Mac's refresh rate.
- **Touch interrupts and cores.** On the handset Touch reads each report on the controller's interrupt and passes it through a shared ring, signalling this process, so a touch reaches the app in front without a poll ([touch.rs](touch.rs)). With seL4 MCS the app in front runs on core 1 at priority 120 with 6 ms of every 8; the others run round robin at 100 on cores 2 and 3; this process and the services stay on core 0. Rust apps can scroll through `violet::Compositor`, which keeps drawing at the panel's rate while the app's main thread is busy.
- **Waiting for events.** The supervisor wires the ARM physical timer to a notification bound to the Open Runtime's thread. Between events it sleeps in one blocking receive, woken by an app's system call or by its own timer (the next touch poll, a thread's deadline, the scan line reaching a waiting present), at priority 150, above the services that poll at 100; long work (starting an app, a USB install) drops back to 100. If the timer does not fire at start, it polls as before. Runtime reads Audio's state from a page Audio publishes, so a status request no longer waits for Audio's hardware loop.
- **Measuring.** `frames` in `/dev/violet/sys` reports what presents cost, how long they waited for the panel, the time from a touch (or from focus) to the app's next present, and the gaps between touch polls; `bench tap X Y N` sends N synthetic presses to the app in front (`bench press X Y N` lifts the finger, a real tap, and also works on the app list). `bench` is taken only over USB (`@sys`), never from an app, and stops while system UI is up. On the handset, `build/moto-package "open-run=@sys bench tap 140 860 20"` and then `"open-run=@sys frames"` put them in the open log.
- **Camera.** `/dev/violet/camera` gives the app on screen the rear camera's raw frames: each `read` returns a 32-byte `CameraFrame` header and the newest frame, once per frame ([abi.rs](abi.rs)). Opening it starts the [Camera service](../../services/camera/README.md); closing it, leaving the screen or the phone sleeping stops it. The frames are copied from a window Camera shares read-only, mapped cacheable: Camera invalidates each slot after the sensor's DMA writes it. The [Camera app](../../apps/open/camera/src/main.rs) develops them with `violet::camera`. The Open Runtime's package may be 0x80000 bytes (others 0x3e000), since its stack is not under its image.
- **Sound.** `/dev/violet/audio` takes 48 kHz s16 PCM (stereo, or mono with `AUDIO_IOC_CONFIG`). It fills a 64 KiB ring shared with the [Audio service](../../services/audio/README.md), which plays it at the shared volume through the speaker or headphones. Built-in sounds take precedence while they play.
- **Network.** TCP and UDP sockets use 32 slots in pages shared with Radio, which runs them on its lwIP stack from its event loop ([sockets.c](../../targets/moto-g-pure/ip/sockets.c)): directly on a joined network, or, for TCP, through the phone's SOCKS5 relay in Phone Internet mode (UDP then fails with `ENETUNREACH`). The slots are one table for the whole phone, shared by rule ([slots.rs](slots.rs)): three are kept for the runtime's own sockets (the Sentinel's link, its flow observer, network time), one app holds at most its floor of two and half of the slots that are neither a floor nor the reserve (5 of 32 with the twelve apps the runtime may run), and an app that already has two gets another only while every other app that may run could still open two. So a second busy app gets nearly as much as the first (4) and every other app keeps its two; a third busy app is left its floor. Past its share an app's `connect` fails with `EMFILE`; with every slot it may use taken, `ENFILE`. Radio never waits on one socket: a connect is stepped a little on each pass of its loop (resolve, connect, the relay's handshake, each with a deadline), so a name that does not resolve or a host that does not answer delays no other socket nor Bluetooth; received bytes go straight into the socket's ring and the TCP window follows what the app has read, and a sending socket may queue only its share of lwIP's heap. A slot is often reused before Radio has seen its close, so Radio alone empties its side of a slot's rings, when it takes the new command, and until then the runtime reads nothing from them: a new connection never starts with bytes of the slot's last one. A socket closed (or left by an exiting app) with bytes Radio has not sent yet lingers, as on Linux: a TCP slot is shut for sending (the bytes go, then FIN) and is closed once they are gone and the peer has closed, a UDP slot once its datagrams are gone, either after 5 s at most ([net.rs](net.rs) `linger_tick`), so `send` then `close` delivers what was sent. A connection that is closing gives its lwIP connection up to the next connect that needs one, and Radio counts the names lwIP is still asking for by app (3 each, however many sockets asked and whether or not they are still open), so one app can use up neither. That heap is still 24 KiB for the whole phone, so many uploads at once are slow, not stuck. A UDP socket takes a slot when it first sends to something other than the resolver, or asks for its address; its rings carry framed datagrams ([net.rs](net.rs)), a full ring drops one as a full interface queue would, `getsockname` gives the phone's real address and port on the network, and each new destination passes the Shield as a connect would. DNS queries (UDP to port 53) never leave the phone: the Open Runtime answers each name with an address in `198.18.0.0/15`, and a connect to one hands Radio the name, which it resolves (or the relay does). The table of those addresses ([names.rs](names.rs)) is bounded and each app has its own: an app keeps 256 names (the least recently used goes first, never one whose address a socket of the app still holds), sees no other app's names or addresses, and loses its names when it exits. An address is not given to another name while any socket holds it, a stand-in address with no name behind it is refused (`EHOSTUNREACH`) instead of being dialled, and a name is passed on whole (up to 253 bytes) or not at all: one that cannot be a host name gets `NXDOMAIN`, and so does one whose last label is a number (`10.0.0.9`, `167772169`, `0x0a000009`, `10.9`): a resolver would dial it as the address it spells, which the Shield never saw. Radio and the emulator's relay refuse such a name too. Only A records get addresses: an AAAA question gets no records (`NXDOMAIN` for a name that cannot be one, as its A question), so programs that ask for IPv6 first fall back to IPv4, and `localhost` (and names under it) is `127.0.0.1` and `::1`, never a stand-in nor a question for Radio. `/etc/resolv.conf`, `/etc/hosts` and the build machine's root certificates are in the image. In QEMU, [tools/net_relay.py](../../tools/net_relay.py) serves the same pages with the Mac's sockets, dialling each connect on a thread of its own; `make test-unit` tests the rules, Radio's socket code and the relay on the host, and `make test-net` (local) runs three apps against them in QEMU (the third serves; see below); `VIOLET_NET_HOSTS` can point names elsewhere for tests, and `VIOLET_NET_UDP=0` refuses UDP like a network that blocks it.
- **Listening sockets and IPv6** ([loopback.rs](loopback.rs), [sockaddr.rs](sockaddr.rs), [sockets.rs](sockets.rs)). `bind`, `listen`, `accept` and `accept4` work on TCP, and a bound UDP socket receives with `recvfrom`. On `127.0.0.0/8` the runtime itself is the network: a connect to a port an app listens on is a pair of byte queues inside the runtime, at once (the Shield sees it as a connect to `127.0.0.1`), and a datagram to a bound loopback port goes into that socket's queue. Only the same app's sockets are reached (App::owner: forked children and the programs an app starts count as the app): a connect to another app's listener is refused (`ECONNREFUSED`) and a datagram to another app's socket is dropped, unless the receiving app's manifest says `serve: apps`. A datagram never goes to port 0 (`EINVAL`, as on Linux) nor to a socket not bound to a port, and a connected UDP socket takes only its peer's. A connection offered to a listener, or bytes sent on a loopback connection, keep the receiving app running for 10 s (`socket_wakes`, a lifecycle reason), so a server in the background does not leave its clients hanging; one never accepted does not keep it for longer. Bounds: 32 KiB each way per connection, 32 connections on the phone and 8 opened by one app (`ENFILE`/`EMFILE`; an app is its owner, not a pid, and the last 6 go only to apps holding fewer than 2, so every app still gets its first `socketpair`), a backlog of at most 8 (a connect past it is refused), 16 datagrams per socket and 256 on the phone (more are dropped). `socketpair(AF_UNIX, SOCK_STREAM)` is the same pair of queues (asyncio needs it). Ports below 1024 are refused (`EACCES`), a port 0 bind takes one from 57344 in rotation (lwIP takes its own local ports from 49152-57343, lwipopts.h, so they never meet), a port a listener or bound socket holds is `EADDRINUSE` (connections do not hold their server's port, so a server can listen again at once), and another of the phone's addresses than the wildcard and loopback is `EADDRNOTAVAIL`. Every `listen` (and a wildcard UDP `bind` offered to the network) passes the Shield as `Bind { port }`; the Shield matches `Bind` only by binary hash and does not record it as telemetry or cut it off in a quarantine (shield.rs), so the runtime itself refuses a network listener or bind to a quarantined app (`EACCES`, accepts too) and logs each network listener. A socket on the wildcard is offered to the network only when its app's manifest says `serve: lan` (otherwise it serves loopback only); a listener or UDP port that is, also listens on the network while the phone is on one (Wi-Fi on the handset, the Mac in QEMU), through one of the app's slots, and `listen`/`bind` wait (up to 5 s) for Radio's answer, so a port Radio cannot take is the call's error (`EADDRINUSE`, `ENOBUFS`), not a socket that quietly serves loopback only. Every connection taken from the network passes the Shield as a connect to its peer's address, and is closed if refused: Radio listens with lwIP ([sockets.c](../../targets/moto-g-pure/ip/sockets.c)), parks arriving connections with their window shut (lwIP drops SYNs past the backlog of at most 4, 8 wait on the phone, below every slot's connections in lwIP's priority), and an `accept` takes the oldest into another of the listening process's slots, so the per-app share holds (a forked worker accepting on an inherited listener accepts for the process that listens). Phone Internet's relay carries outgoing connections only, so there (and when the phone is offline at `listen`) a wildcard listener serves loopback only; it does not start listening on the network later. In QEMU the relay listens on the Mac's `127.0.0.1` only (`VIOLET_NET_LISTEN` maps ports for tests), and a loopback port no app listens on is still the Mac's, as tests expect. `AF_INET6` sockets take the IPv6 forms of what the runtime carries: `::ffff:a.b.c.d` is that IPv4 address, `::1` is `127.0.0.1` and `::` the wildcard, so dual-stack servers and v4-mapped clients work; any other IPv6 address is `ENETUNREACH` (`EADDRNOTAVAIL` for `bind`). Addresses come back in the socket's family, `127.0.0.1` as `::1`. `IPV6_V6ONLY` is accepted and ignored.
- **Bluetooth.** `/dev/violet/hci` gives up to four open apps at once (one descriptor per process and per app, and one of the four places kept for core apps; more get `EBUSY`) the Bluetooth controller's HCI ([hci.rs](hci.rs)): each `write` is one H4 command or ACL packet, each `read` one event or ACL packet for that app, `poll` works, and both give `ENETDOWN` while the controller is off. The runtime owns the controller and shares it ([hcimux.rs](hcimux.rs)): one command at a time goes to the controller and its answer only to the app that sent it; a connection handle belongs to the app that made the connection (the initiator whose create the controller accepted; for a peripheral link the app advertising with legacy advertising at that moment, or the owner of the extended set that LE Advertising Set Terminated names; a link nobody can be shown to own is disconnected), its ACL data and events go only to that app, and ACL or a command naming another app's handle is refused (`EPERM`, status 0x02); controller ACL buffers are counted for everyone and Number Of Completed Packets is split by owner; scanning is shared (every scanning app gets every advertising report; duplicate filtering only while one app scans); legacy advertising (from the app's first advertising command until it turns advertising off; a command the controller refuses gives back an unconfirmed claim), each extended advertising set, and creating a connection belong to one app at a time, and the random address may be set only while no other app holds advertising (others get Command Disallowed, 0x0c); the controller takes either legacy or extended advertising, scanning and initiating commands until reset, so a command of the other kind is refused while the first kind is in use and otherwise the runtime resets the controller first; a command the controller does not answer in 3 s gets 0x1f, and its opcode is not sent again until the late answer has come (and is dropped) or 9 s have passed; event masks are per app (the controller gets their union, an ordinary app may unmask only the events routed to apps, nobody Enhanced Connection Complete v2, and each app gets LE Connection Complete or the Enhanced one in the form it unmasked). An ordinary app's Reset resets only its own state, and vendor commands, controller configuration, filter lists, BR/EDR and anything else not on the list get 0x0c unless the app is a core app from the boot image (Home, Settings, Installer), whose commands pass. Closing the device (or the app dying) disconnects the app's links and stops its advertising, scanning and connection attempt (a create still queued is just dropped). A system app's Reset or a Radio restart ends every link and gives each app that was scanning, advertising or connecting Hardware Error. `make test-unit` runs these rules against a scripted controller, with bitchat's own BLE host as one of the clients ([tests/hci_host.rs](tests/hci_host.rs)). Not yet: pairing/bonding keys and GATT shared between apps (each app still runs its own host stack; a Bluetooth host service would), and the multiplexer has not run on the handset's controller. On the handset Radio carries it over the connectivity chip's STP link ([bt.rs](../../targets/moto-g-pure/bt.rs)), so it runs while Wi-Fi is joined; in QEMU no controller is attached yet. [bitchat](../../apps/open/bitchat/README.md) is its first user.
- **Microphone.** `/dev/violet/mic` streams 16 kHz s16le mono samples to an app whose manifest has `mic`: while one is open, Audio copies every sample into an 8-page ring after the PCM ring and the Open Runtime returns what arrived since the last read (blocking, `poll` works). The microphone stops when its app leaves the front and starts again when it comes back, except for an app with `mic` and `system` (the voice agent): while it holds the microphone it keeps listening behind other apps, `status` says `listening=1` and Home shows a green microphone. A paired agent (`peer` in `/data/agent`) starts behind Home when Home starts.
- **Installed apps** ([appstore.rs](appstore.rs)). `install NAME TITLE` in `/dev/violet/sys` commits the agent’s staged program as `/apps/NAME` and gives it a Home icon under TITLE. After a successful replacement, the next launch starts the new version; `uninstall NAME` and `installed` complete it. Only apps with `system` (the built-in agent, Settings and Home) may install and uninstall, and no installed app may take a name whose `/data` a built-in app shares; only they can write the staging file `/apps/.agent-install`. Uninstalling ends a running copy and removes the app's /data files and its consent answers. A program may carry its manifest at its end (`VMF1`, see Policy), which the store keeps with it. On the Moto, Storage keeps installed apps in the last 12 MiB of boot_b by default. The storage-preserving flash skips this range. If the owner has explicitly claimed Android userdata with `moto-flash --take-userdata`, Storage uses that partition and migrates the installed apps. QEMU uses sectors 4096 onward of its 16 MiB disk. Programs move through a 64 KiB window shared with Storage; a directory kept in two copies is rewritten only after the program is flushed, so a power cut leaves the old set or the new one. An install whose data starts with `VGZ1` (a gzip of a cpio archive) is a package: it is unpacked into `/bin` and `/lib` (nothing else) at every start, gets no Home icon, and Settings does not offer to delete it; Python reaches the handset this way.
- **Full-system updates** ([update.rs](update.rs)). `update info|manifest|check|write SECTOR|hash FIRST COUNT|apply` in `/dev/violet/sys`, for Settings and the agent only: each piece of a signed bundle (staged in the caller's own `/data/NAME.ota-staging`, which no other app can reach, at most 64 KiB) goes to the inactive boot slot through Storage, which hashes what it reads back; `check` and `apply` ask the supervisor, which alone can switch slots ([package manager](../../system/package-manager/README.md#full-system-updates-ota)).
- **Files.** `/apps`, `/bin` and `/lib` come from the image. Writes go to an in-memory layer over it. Each app sees only its own part of `/data` (see Policy). Files directly in `/data` (names of up to 16 letters, digits, `.`, `_` or `-`, up to 4 KiB) are kept across restarts by the Storage service ([data.rs](data.rs)): the Open Runtime loads them at start and writes one back after it changes, a few messages per pass of its loop, whole and in one commit, so a power cut leaves the old file or the new one; `fsync`, `fdatasync` and `sync` return after the write-back, with an error when the file is not stored (`EIO`, `ENOSPC`, `EFBIG`, `EINVAL`) and `EINTR` when one call was not enough or the app has used up its allowance of syncs. A rename is two commits (a cut can leave both names; with all 32 files in use it can lose the file). A failed save is tried again. The rules are in [writeback.rs](../../services/storage/writeback.rs), see [Storage](../../services/storage/README.md). Storage keeps 32 such files for all open apps; everything else is lost at restart.
- **Home and /dev/violet/sys.** `/apps/home` starts the first time the open apps come to the front and stays running. `home` brings it back; `open PATH` brings an app to the front or starts it; `apps` shows the plain list of every program; `running` lists running programs; `status`, `audio`, `volume N|up|down`, `sound NAME`, `mic record|listen|off` and `log TEXT` cover the rest. An app leaving the front stops the microphone.
- **Wi-Fi.** `wifi scan`, `wifi list`, `wifi join ID [PMK]`, `wifi leave` and `wifi` (the state) in `/dev/violet/sys`, served by [wifi.rs](wifi.rs). Radio's requests run as Runtime tickets, so a join that takes seconds on the handset does not stop other apps. Any app can scan and read the state; only an app with `wifi-admin` (Settings) may join or leave. [Settings › Wi-Fi](../../apps/open/settings/src/wifi.rs) turns a typed password into the WPA2 key (PBKDF2-SHA1 with the SSID) and sends only the key. The auto-connector in wifi.rs rejoins the networks the app saved in `/data/networks`: 8 s after boot (a saved Phone Internet goes first), then with waits growing from 30 s to 10 minutes while none is in range, and every 30 s it checks a joined network is still joined. It tries each saved network in range, most recent first (a failed one waits for the next round, a refused key included: a lost handshake frame can look like a wrong key), and pauses after the app leaves a network.
- **Phone Internet and Bluetooth.** `relay` reports Phone Internet (`state=off|starting|waiting|joined|online|unavailable|busy`); `relay on CODE` and `relay off` start and stop it, from an app with `wifi-admin` only (Settings), which keeps its choice in `/data/relay`. Three seconds after boot the runtime turns a saved "on" back on. `bluetooth` answers whether the controller is up and whether an app has `/dev/violet/hci` open.
- **Wake locks and Power.** `wakelock 1` keeps the CPU awake after the screen goes off, `wakelock 0` releases it; it lapses ten minutes after it was last taken and ends with the app. Any app may ask (there is no manifest permission for it), so it is bounded instead: with the screen off no lock is newly given and a held one lasts at most thirty minutes however often it is renewed (`error screen-off`), until the screen is on again; `error busy` means Power's table of 16 is full. The runtime logs which program took, released or lost a lock. `wakelocks` lists who holds one (by pid) and each holder's totals; `power` reports the thermal level, operating point and a battery percentage (`sensor=0 dvfs=0` on the handset, which has neither yet). The [Power service](../../services/power/README.md) keeps the accounting; [powerctl.rs](powerctl.rs) is the glue.
- **Wall clock.** `CLOCK_REALTIME` starts at the image's build time. Five seconds after a Wi-Fi network (or the emulator's host) is up, the runtime asks three NTP servers ([sntp.rs](sntp.rs), [timesync.rs](timesync.rs)) and sets the clock if two agree within two seconds; it asks again every six hours, and after a failed round at intervals growing from two minutes to an hour. Each server is asked twice in a round of at most eight seconds: once by name, to learn its address, then at that address for the time, so a slow name lookup is not counted as network delay. Every request carries 64 random bits of its own from the random generator (no round starts without it), and an answer must echo them, come from port 123 of the address the request went to (one address counts for one server only), come from a synchronised server within one second, and name a time between the image's build and twenty years later; a clock already set moves by more than ten minutes only if two rounds running say so. `time` reports `unix= synced= age= rounds= failed= refused=`. SNTP is unauthenticated: a network that forges every answer, or the paths to two of the three servers, can still set the time inside those limits; one server, or the path to one, cannot. The time can be out by half the round trip plus the runtime's polling (50 ms). Phone Internet carries no UDP, so the clock is not set over it, and the time is not kept across a restart (no RTC driver).
- **Policy** ([policy.rs](policy.rs), [manifest.rs](manifest.rs); host tests in [tests/policy_host.rs](tests/policy_host.rs), `make test-policy` in QEMU). Default deny. An app is the owner Violet Shield derives for it (`/apps/NAME` is NAME). Its powers come from a manifest of `caps:` (`net`, `audio-out`, `mic`, `camera`, `hci`, `wifi-admin`, `system`) and `data:` (files directly in `/data` it shares) lines: a built-in app's is `apps/open/NAME/manifest.txt`, which [build_initfs.py](../../tools/build_initfs.py) checks and packs into `/apps/.manifests`; the runtime reads that file from the image itself, never from what was written over it. An Agent-built app's manifest travels at the end of its program (the text, its length, `VMF1`; written by [agent_build.py](../../tools/agent_build.py)). An app with no manifest, a program pushed over USB or written since boot, or one started from outside its own `/apps` folder, gets only its own `/data`, the screen, touch and the unprivileged sys commands. `wifi-admin`, `system` and shared files count only in the image's manifests. Checked where each power is given: `socket` (`net`; `EACCES`), the open of `/dev/violet/audio`, `mic`, `camera`, `hci` (`EACCES`; an unknown `/dev/violet` node is `ENOENT`), and the sys commands `open`, `launch`, `install`, `uninstall`, `shield-agent`, `shield-mode`, `shield-release`, `update` (`system`), `wifi join|leave` and `relay ...` (`wifi-admin`), `mic` and `sound`/`volume` (`error not allowed (needs CAP)`). Files: an app sees and can make only `/data/NAME` (a file, or a folder and all in it) and `/data/NAME.*`, plus what its image manifest shares (Settings: `networks`, `relay`); another app's files and the runtime's dot files (`/data/.settings` with the shared settings, `/data/.grants`, `/data/.shield-mode`, `/data/.lock`) answer `ENOENT` to open, stat, access, chdir and readlink, are left out of a listing of `/data`, and answer `ENOENT` to writes too, so an `O_CREAT` open (a read of a file that is there, a write of one that is not) cannot tell whether they exist. `/apps`, `/bin`, `/lib`, `/etc` and the root are read-only (`EROFS`); `/tmp` is shared by all apps except its dot names, which only the image apps whose manifests list them on a `tmp:` line reach (Settings: `/tmp/.ota-chunk`; Music and the Agent: `/tmp/.locomo.*`), so no app can feed the privileged apps' inputs. An app that `execve`s (or spawns) another app's `/apps` program does not become that app: the program keeps the caller's owner and counts as written since boot, so it gets the minimal profile, no Shield core role and none of Settings' or the Agent's path checks (`policy::exec_crosses`, manifest.rs `exec_identity`), since the caller chose its arguments, environment and descriptors; only Home, Settings and the Agent (and the user, through them) start an app as itself. Paths are judged after the runtime resolves `.`, `..` and `//`, and there are no links. Violet Shield sees each attempt first, so its telemetry is unchanged. Net, the microphone, the camera and Bluetooth (`hci`) of an Agent-built app are asked of the user through the trusted UI (`policy::ask` answers `Ask`, [trusted_ui.rs](trusted_ui.rs) `request_consent`); while the prompt is up the `open` or `socket` waits for the answer (`Wait::Consent`; `EAGAIN` with `O_NONBLOCK`) and then runs again, so the answer decides it (a prompt withdrawn because the app left the screen gives `EACCES`); the answer is kept in `/data/.grants`. An app asks ahead with `consent CAP` (Python `violet.ask`), which prompts only for a power its manifest declares and the user has not answered. Every install of a name, new or over an old one, and every uninstall clears that name's answers, both the kept ones and the trusted UI's for this boot. Installed app names are at most 12 characters, so `/data/NAME.KEY` fits Storage's 16; violet.py hashes longer keys. The first start moves the shared settings from `/data/settings` (now Settings' own name) to `/data/.settings`. Not covered: only names directly in `/data` are kept across restarts, so an app's folder `/data/NAME/` lasts until the next restart; `/tmp`'s other names are shared; `/data/.grants` and `/data/.settings` are plain text with no integrity check of their own, so they are only as safe as the storage under them (anyone who can write the medium can grant an installed app net, mic, camera or hci; authenticated, encrypted `/data` is A3-enc-data); a sys command that needs a consent power (`mic`) is refused while asking rather than waiting (apps ask ahead); an app installed over another of the same name keeps its `/data` (only its answers go); flat `/data/NAME` files that Agent apps saved before per-app namespaces belong to no app and are no longer reachable; the lifecycle's priority checks still compare the program's path; there is no screen for reviewing or revoking consent answers yet; the developer's USB push still runs code (with the minimal profile); the runtime itself (component 24) holds every app's memory, the sockets, the microphone and camera rings, so the policy is only as strong as the runtime.
- **Trusted system UI** ([trusted_ui.rs](trusted_ui.rs) draws and wires it, [sysui.rs](sysui.rs) holds the rules; host tests in [tests/sysui_host.rs](tests/sysui_host.rs), `make test-trusted-ui` in QEMU). The Open Runtime owns the final copy to scanout, so it keeps part of the screen for itself. *The band*: the top 32 rows over every app are drawn by the runtime: the app's title from the image's `/apps/.home` (an Agent-installed app shows its file name and `INSTALLED`, never the title it chose), `MIC` while any app has the microphone open and `CAM` while the camera is on, and, while system UI is up, `VIOLET SYSTEM` on the accent colour with `LOCKED`, `PASSCODE` or `PERMISSION` (and still `MIC` and `CAM`). It is redrawn when the program in front changes, an in-place `execve` included. Presents never write those rows and a touch that starts on them never reaches the app (holding it a second still goes Home). *Prompts*: `request_consent(pid, owner, cap)` (policy.rs calls it; `consent net|mic|camera|hci` in `/dev/violet/sys` lets the app in front ask ahead: `allow`, `deny` or `pending`) shows the app's runtime-derived name and what it wants over the app. Only an Agent-installed app's declared net, mic, camera or hci, still unanswered, raises one (policy.rs `ask` answers `Ask`; for anything else policy's answer stands, so no prompt asks what the user cannot decide), and only the app on screen, one at a time; an answer holds for the boot, so a denied app cannot nag (policy.rs keeps it across restarts). *The passcode pad and the lock screen* are drawn the same way. While any of these is up the app in front hears `FOCUS_LOST`, its presents are dropped, every real touch goes to the runtime, synthetic touches stop, nothing records (the microphone is turned off, the agent's background listening too, and neither the microphone nor the camera starts until it goes), and the camera returns nothing; touches the runtime takes do not count as the user touching the app for Violet Shield. A button counts only once the overlay has been drawn (touches before that are not judged), for a press that lifts on the same button after any finger already down has lifted: on the keypad one that starts 400 ms after it appeared, on a prompt one that starts after 700 ms with no touch at all, so tapping the ALLOW spot over and over never answers it. *Passcode*: Settings › Passcode writes `passcode set` or `passcode off` (Settings in front only); the runtime then asks for the current passcode and the new one twice on its own keypad, so no app (Settings included) sees the digits. 4 to 12 digits, PBKDF2-HMAC-SHA-256 with 100,000 iterations and a 16-byte salt from the random generator, computed a slice per pass of the loop; the record (`/data/.lock`, which `at` refuses to every app) holds the failure count, which is written back to Storage before each attempt is checked (an attempt that cannot be saved is not checked). After five failures each attempt waits 30 s, doubling to an hour; a restart starts the wait again in full. A damaged record keeps the phone locked, and so does a `/data` that Storage could not list in full at boot (a missing record proves nothing then; every slot `OFFLINE`, Storage with no disk, is the one exception). The phone locks at boot when a passcode is set, after five minutes without a touch, from Home's Lock (shown while a passcode is set), on `lock` (the app in front or a system app), and when the screen goes off (Runtime reports focus 0 while asleep; nothing sends Runtime's sleep yet, so today that is the idle lock); while locked, `open`, `launch`, `home`, `apps`, `mic`, the microphone and USB starts of programs are refused. *Notifications*: `notify TEXT` (any app; the last eight are kept, titled by the runtime, an installed app's always starting `INSTALLED`); Home alone reads them (`notifications`) and shows the newest under the date; the lock screen shows only how many there are, with Violet Shield's warning count. *Commands*: `bench` comes only over USB (`@sys`); `open` and `launch` only from the app on screen, Home or the Agent; `home`, `apps` and `mic` only from the app on screen; `volume` and `sound` from it or a system app; `set relay|stun` only from a system app or USB. Not covered: biometrics (no sensor driver); a full keyboard for secrets (the Wi-Fi password is still typed on Settings' own keyboard, which only Settings sees); the lock is a screen lock, not data protection: `/data` is not encrypted, the record is not bound to hardware (a dump of storage allows an offline guess of a short PIN), and the developer's USB path (`moto-flash`, fastboot) can still replace the image; built-in Runtime apps and the classic launcher shown by the Display service get no band and are not behind the lock (it covers the open apps only); deleting `/data/.lock` from the storage medium removes the passcode (no sealed or hardware-backed marker); the band and prompts live in the same process that serves every app's system calls.

## Not done yet

- Real IPv6. `AF_INET6` sockets carry IPv4 (mapped) and loopback addresses only; Radio's lwIP has no IPv6 (it would add about 38 KiB to Radio on the handset, more than Radio's room), so IPv6-only networks and IPv6 literals do not work. No `AF_UNIX` paths (only `socketpair`), no `SO_REUSEPORT`, no inbound connections over Phone Internet, and listening on the handset's Wi-Fi has not been run on a phone yet. `serve: lan` and `serve: apps` are the manifest's word alone (no consent prompt, also for Agent-installed apps); the Shield has no telemetry event for listening; loopback ports are one namespace for the phone, so an app with `serve: apps` can take a port first (another app's bind is then `EADDRINUSE`); a UDP socket on the wildcard of an app without `serve: lan` still takes its port on the network once it sends there, as any client socket does; and two cooperating processes can keep each other running by talking on loopback, as sending on the network can.
- Larger persistent files. `/data` keeps 32 files of up to 4 KiB (installed programs have their own store).
- Go apps still start with `GODEBUG=asyncpreemptoff=1` (mod.rs): signals are delivered now and `make test-abi` runs Go without it (the Go test program execve's itself without it), but it stays until that suite has passed on the emulator and the handset.
- Copy-on-write `fork`, job control, CPU-time timers, `signalfd` (see Signals and Processes above); dynamically linked libraries other than libc (`dlopen` needs executable `mmap`).
- Executable memory made at run time (a JIT, `dlopen`): refused by the W^X policy, with no per-app exception.
- Protection finer than the 64 KiB hardware page, position-independent builds of the shipped apps, and a hardware entropy source (see Memory protection above).
- Up to twelve apps at once (seven with 4 MiB of kernel memory), on four cores (the second cluster of the MT6765 is not used). A wake lock does not yet keep an app from freezing behind Home, and a background download (receiving only) freezes like any cached app.
- A CPU that idles. The Open Runtime sleeps on its timer, but the services' `delay_ms` is a yield loop (runtime/transport.c) and Audio, Camera, the launcher and the supervisor's watchdog loop poll with it, so nothing ever waits for an interrupt: QEMU uses a whole host core at Home (`make test-idle` measures it).
