# Architecture module

Everything that differs between the AArch32 system VioletOS ships and the AArch64 port in progress, in one place: [mod.rs](mod.rs) and the generated [linux.rs](linux.rs). It is pure `no_std` Rust with no kernel access, so `make test-unit` runs all of it on the host for both architectures ([tests/host.rs](tests/host.rs), through [test_host.sh](test_host.sh)), and it compiles for both `armv7a-none-eabi` and `aarch64-unknown-none`.

| Piece | What it holds |
| --- | --- |
| `Abi` (`AARCH32`, `AARCH64`, `NATIVE`) | Word size, ELF class and machine, top of user space, stack alignment, the frame sizes the kernel offers, the page-table levels, where the program counter, stack pointer, status register and thread pointer sit in the kernel's thread context. |
| `decode_syscall`, `syscall_return` | A thread's Linux system call out of the kernel's unknown-syscall fault message, and the reply that returns from it. AArch32: the number is r7 and the instruction is 4 or 2 bytes (Thumb). AArch64: the number is x8, which needs the [kernel patch](../../kernel/sel4/aarch64/README.md). |
| `decode_vm_fault` | Read, write or execute, from DFSR (AArch32) or ESR_EL1 (AArch64). |
| `map_frame` and the `Kernel` trait | Map one frame, creating the page tables the address still lacks: one level on AArch32, up to three on AArch64. The kernel is behind a three-method trait; the tests supply a model of seL4's page tables. |
| `Elf` | ELF32 and ELF64 static executables to the same segment list. Refuses the other architecture's programs, position-independent ones, writable-and-executable segments, segments outside user space (empty ones included, which are then never handed to a loader) and two segments that share a page, so a page-granular loader never merges protections. `Segment::page_span` is the checked page rounding a loader uses. |
| `build_stack` | The initial stack (arguments and auxiliary vector) in the ABI's word size and alignment. |
| `counter`, `counter_frequency` | The generic timer's virtual counter: CP15 on AArch32, a system register on AArch64. |
| `internal_call` | An AArch64 call number translated to the one (AArch32) numbering the Open Runtime's dispatch, policy and Shield hooks know, with its `Layout`; never the raw number (63 is AArch64's `read`, AArch32's `dup2`), and None (ENOSYS) for numbers the table lacks, AArch32-only calls and the AArch32 private range. |
| `enter64` | An AArch64 program's call as the Open Runtime's one dispatcher takes it: the AArch32 call of the same meaning with its arguments in 32-bit words and, beside them, the same arguments as the 64-bit registers held them (`wide`, moved with them where a call is rewritten), which the dispatcher reads every address and length of app memory from (in the 32-bit words an address or size argument of 4 GiB or more, sign-extended ones included, and any other word above 4 GiB that is not a sign-extended int, becomes an address in no app's regions, so EFAULT, never cut to a low one: `memory_args` names each call's address and size arguments), 64-bit values rewritten as AArch32's register pairs (lseek, pread64, ftruncate, fallocate, fadvise64, mmap's byte offset as pages), calls AArch32 makes another way (nanosleep as clock_nanosleep, getrlimit/setrlimit as prlimit64, gettimeofday as clock_gettime64), and the structures the dispatcher fills in (stat, timeval, sysinfo, rusage, statfs, tms) converted after it ran (`After`). Pointer-holding structures (iovec, msghdr, sigaction, stack_t, argv, clone) are read by the dispatcher itself in the app's layout; the rest answer ENOSYS (`unconverted` names them). |
| `signal64` | The Linux AArch64 `rt_sigframe` (siginfo, ucontext, sigcontext at 304, `__reserved` at 592 with `fpsimd_context`, `esr_context` for faults and the null record, then the {fp, lr} frame record), `place`/`encode`/`decode` (sigreturn keeps only NZCV of pstate, refuses a misaligned or kernel pc and a frame without its fpsimd record), the register state a handler enters with, and the signal gate's instruction words (PR #48's gate: q0-q31, FPSR and FPCR into the frame, `blr x3`, back, `rt_sigreturn`) with the fork helper after it. The tests decode the gate's store offsets against the frame. |
| `compat` | The `Layout::Words` structures for either ABI: AArch32 `stat64` to AArch64 `stat`, timeval, rlimit (RLIM_INFINITY in each width), rusage; and readers for the pointer-holding ones (iovec, msghdr and its outputs, cmsghdr with its 12- or 16-byte header, the kernel `sigaction`, `stack_t`), plus mmap's byte offset as mmap2's pages. |
| `linux` | Linux system call numbers of both ABIs, generated from the kernel's own headers by [gen_linux.py](gen_linux.py), with the AArch32 call each AArch64 call corresponds to (AArch64's `clock_gettime` is AArch32's `clock_gettime64`, `mmap` is `mmap2`, and so on) and whether its arguments and structures have the same layout (102 calls) or differ with the word size (50). |

## Who uses it

The 64-bit bring-up target ([targets/qemu64](../../targets/qemu64/README.md)), whose bootstrap task runs this code on a real AArch64 seL4 kernel, and the Open Runtime, which includes it as `crate::process::arch` (runtime/open/mod.rs). On AArch64 the runtime reads the counter through it, and runtime/open/sys.rs has the 64-bit kernel interface beside the 32-bit one: `tcb_read_context`/`tcb_write_context` (the 36-word `Context`) and `receive64`/`reply64`/`send64` (whole 64-bit message registers), backed by AArch64-only functions in sel4.c, whose 19-word `Regs` forms refuse on AArch64 rather than overrun. The runtime's own pure AArch64 pieces sit with their AArch32 forms: `elf::plan64` (ELF64, PIE, PT_INTERP naming only `/lib/ld-musl-aarch64.so.1`, W^X) and `vma::Layout64` (a sparse 47-bit layout above 4 GiB with 22-28 random bits per band and tens of TiB of mmap room). On AArch64 the dispatch runs 64-bit programs through them: the loader takes ELF64 through `elf::plan` (`plan64`, whole addresses) and places it by `Layout64`; regions, pages, page tables, copies and the W^X rules use whole 64-bit addresses (`vma::Va`, for AArch32 apps too), and the dispatcher reads every address and length of app memory from the call's 64-bit registers (enter64 `wide`, syscall.rs `vargs`), never from the 32-bit words; mmap and brk answer their whole address (sys.rs `set_result`), and a program counter the runtime moves keeps its high bits (enter64 `widen`). It builds the stack in 8-byte words and starts threads with a whole `Context` (no trampoline); each call goes through `enter64` (runtime/open/abi64.rs) and its answer keeps the thread's 64-bit registers (sys.rs `calls`, `enter64::widen`: x0 of an answered call is always its result, an error sign-extended, even when it equals the call's own x0); signal handlers run with `signal64`'s frame through its gate (abi64.rs `deliver64`, `sigreturn64`), clone and vfork start threads from the parent's whole context, and fork goes through the A64 fork gate (abi64.rs `fork_gate64`). On AArch32 the dispatch is unchanged but for the wider address type.

## Where the existing code stands on AArch64

The table this section held measured, by compiling alone, how far the 32-bit sources were from AArch64. That gap is closed for QEMU: [targets/qemu64/stack.py](../../targets/qemu64/stack.py) builds every layer for AArch64 and `make qemu64 QEMU64_STACK=1` boots and checks them ([targets/qemu64](../../targets/qemu64/README.md#the-violetos-system-on-aarch64)).

| Layer | On AArch64 |
| --- | --- |
| Component crates, Power, `runtime/transport.c`, the C shims | Built and run. The counter reads (`transport.c` `ticks`, Power) use the system registers on AArch64. |
| `system/supervisor/supervisor.c` with `platform/sel4/board/memory.h` and `platform/sel4/include/vm.h` | Built and run as the root task on QEMU and on the handset (entered at `platform/sel4/loader/root64.S`; the handset's build is `targets/moto-g-pure/build64.py`, `make moto64`). On the handset a 1 MiB window is 256 pages, and Camera's 4 MiB frame window is two 2 MiB frames ([targets/moto-g-pure](../../targets/moto-g-pure/README.md#aarch64-boot-path)). |
| Open Runtime | Built and run; 64-bit programs go through `enter64`, `signal64` and `compat` into the one AArch32 dispatcher, with their addresses whole, placed by `vma::Layout64` above 4 GiB. |

What still holds: `seL4_ARM_LargePageObject` is 64 KiB on AArch32 and 2 MiB on AArch64, so on AArch64 `memory.h` maps each window as consecutive frames of the largest size its length and alignment allow (`frame_size`), never one 64 KiB frame, and every `u32` that holds an address is correct only while all mappings stay below 4 GiB (the board descriptions keep that rule).
