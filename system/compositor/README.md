# Compositor

The compositor decides what reaches the screen and who gets a touch. Its rules are plain Rust with no hardware in them, so the same source runs in the Display process and in host tests:

| File | What it holds |
| --- | --- |
| [scene.rs](scene.rs) | Who owns which rows (system band, system cover, the client in front), what a client's submission may change, damage rectangles, where a touch goes, and the frame budget record. |
| [blit.rs](blit.rs) | The software blits: copy, fill and the 3x widening of a built-in app's row. NEON on 32-bit Arm, plain loops elsewhere. |
| [display.rs](display.rs) | Composition: a present becomes damage, damage becomes blits into scanout, and the cost is measured. Hardware sits behind the four-method `Hardware` trait. |
| [gate.rs](gate.rs) | What Runtime refuses while the phone is locked. |
| [tests/host.rs](tests/host.rs) | Host tests, part of `make test-unit` (under a second). |
| [tests/neon/](tests/neon/) | The NEON loops and the built-in-app path on an emulated Arm core, bare metal. Run `tests/neon/run.sh` after changing blit.rs; it is not part of any make target. |

The [Display process](../../services/display/process.rs) is this code over the real framebuffer.

## What is enforced today

- **Built-in apps are drawn only by the compositor.** Display is the one process that reads their surfaces and composes them into scanout. It is not the only writer of scanout: the Open Runtime still maps it writable (supervisor.c `share_scanout_with_open`), so it can draw over a built-in app's pixels and rewrite the tail records below. A present is clipped by `Scene::submit` to the screen; the band and cover rows (`set_band`, `set_cover`) are never set in Display today, so live they protect nothing and are exercised by the host tests only. The pixels are the same as before the compositor existed (a host test compares every pixel with the old loop); a source row is now read once and widened with NEON instead of being written pixel by pixel twelve times. With the Open Runtime installed the launcher never presents and opens only the open apps, so on a normal boot this path is barely used (the sleep clear uses the NEON fill); tests/neon/ runs the NEON loops on an emulated core. The loops leave d0-d7 undeclared, which is only correct in this soft-float build; blit.rs refuses to compile for the hard-float ABI.
- **Damage.** Changes are kept as up to eight rectangles that neither overlap nor touch; more than eight separate changes fall back to their bounding rectangle. Only damaged rows are drawn and reported to the QEMU viewer.
- **A measured frame budget.** Every composition is timed with the board's counter against a budget of 8 ms (`FRAME_BUDGET_MS`). The record is published in the words after the visible frame, at word 16 of the tail (`STATS_AT`; the viewer's dirty record is at word 0): magic `CMPS`, counter ticks per millisecond, compositions, compositions over budget, the last, the worst and the total time in ticks, and pixels written in units of 1024. In QEMU it is at guest physical address `0x79450000 + 720*1600*4 + 64`. Nothing reads it automatically yet, no handset number has been taken with it, and since the Open Runtime can write the same words it is not proof of Display's measurement.
- **Built-in screens are behind the lock.** The Open Runtime reports with each focus poll whether its lock screen is up, and Runtime counts the phone as locked from the moment it sleeps (EXECUTE POWER 1, when the Open Runtime is installed), not from the next poll. The Open Runtime's first poll after a sleep is answered 0 even if the phone is awake again, so it locks (if there is a passcode) however quickly the wake came; its next poll then says what it decided. At the wake itself (the launcher's POWER 0 or a touch on the screen that was in front) a locked Runtime puts the open apps in front and stops the microphone, so the built-in screen from before the sleep gets no touch, present or sound in between. The Open Runtime is told it is in front only once no built-in app's present is still with Display, so an earlier present cannot be drawn over the lock screen. While locked, Runtime refuses from every client anything that moves the focus (`OPEN`, `QUIT`), and from everyone but the Open Runtime presents, volume, playback, the microphone, installs, removals and Phone Internet ([gate.rs](gate.rs)). The launcher's radio switch is let through: its boot restore of the saved choice and the Mac's USB Wi-Fi job are sent once and not retried, and show nothing. Host tests in runtime/process.rs (run through runtime/open/tests/broker_host.rs) drive the real `dispatch` and `contact` through every order of five sleeps, wakes, polls, opens, quits and touches and check that, locked and awake, only the open apps are in front. If the Open Runtime stops polling while locked the lock stays (the launcher has no screen of its own, so there is nothing to fall back to, and a lock that lapsed when its owner went quiet could be dropped by wedging it); the supervisor's warm restart keeps its memory, and a cold start locks again from the saved passcode.

## What is not enforced yet

The Open Runtime still maps scanout and still draws the band, the lock screen and the permission prompts itself ([trusted_ui.rs](../../runtime/open/trusted_ui.rs)). It is one process with every open app's system calls, so a bug in it can draw over system UI, read touches meant for the passcode pad, or tell Runtime the phone is unlocked. The scene rules for that case (band rows, cover, gesture ownership, synthetic touches) exist here and are host-tested, but nothing on the device calls them for the Open Runtime. Moving it is the next step, and was not done in this change because it replaces the only display path of the open apps and could not be booted while it was written:

1. **Supervisor.** Stop sharing scanout with the Open Runtime (`share_scanout_with_open`). Give it instead 1,126 pages of ordinary memory at the same address (its "screen" becomes a surface), mapped read-only into Display. That is 4.6 MiB; on the handset it has to come from a spare untyped, which has not been checked. Move the touch ring (`0x09807000`) and DISP_RDMA0 (`0x09804000`) mappings from the Open Runtime to Display, and give the Open Runtime a badged capability to Display's endpoint.
2. **Display.** Serve `present_surface` for the Open Runtime (already written and host-tested), with the beam wait from runtime/open/scanout.rs. Take over sysui.rs (the passcode, prompt and band rules are already free of the runtime) and the drawing half of trusted_ui.rs. This needs SHA-256 in Display, a store for the passcode record that the Open Runtime cannot rewrite, and room: Display is 4,096 bytes of a 253,952-byte window, but the handset catalog bank has about 20 KiB left in total.
3. **Open Runtime.** Replace `clean_framebuffer` and `mark_dirty` with a damage message; ask Display for prompts and wait for the answer; receive touches from Display instead of the ring and Runtime's poll. trusted_ui.rs then shrinks to the calls.
4. **Cost.** Every open-app frame is copied twice (app buffer to surface, surface to scanout). At the copy rate runtime/open/scanout.rs states for the handset (about 500 rows a millisecond), a full 720 x 1600 frame goes from about 3 ms to about 6 ms, inside the 8 ms budget only without waiting for the beam. This must be measured on the phone before it ships; mapping app buffers into Display directly would avoid the second copy and needs the supervisor to own surface memory.

## Graphics hardware: what there is, and what a driver would need

Everything on this page is software. Nothing here uses, or claims to use, the GPU or the video decoder.

**GPU.** The Moto G Pure's MT6765 has an Imagination PowerVR GE8320 (Rogue, Series8XE). There is no open driver for it: Android uses Imagination's kernel module with closed user-space libraries (the GLES and Vulkan drivers and the shader compiler), built for Android's C library. Mesa's open `powervr` Vulkan driver and the Linux `drm/imagination` kernel driver cover a few other Rogue cores, not this one. A driver on VioletOS would need all of:

- power and clocks: the MFG power domains, the GPU clock mux and gates, and the PMIC rail, sequenced as the vendor kernel does (none of these are mapped to any process today);
- the GPU's register block and interrupt given to one driver process, plus physically contiguous memory it can hand to the GPU's own MMU;
- the firmware the GPU's embedded processor runs, which is a signed binary we have no licence to ship;
- the kernel half ported to seL4: device MMU page tables, the firmware command queues, power-down and recovery after a hang;
- an open user-space driver for GE8320 (shader compiler included), which does not exist. Without it the kernel half has nothing to talk to;
- a way to test it: QEMU has no model of this GPU, so every step is on the handset, where a mistake blanks the only console.

The realistic route to hardware help on this phone is not the GPU but MediaTek's display engine (DISP_OVL hardware layers; phase 4 of [the frame pipeline RFC](../../docs/8ms-frame-pipeline-rfc.md)): the app's buffer and the system band as two hardware layers, so a present is a register write instead of a copy and the band is out of every client's reach. Only DISP_RDMA0's line counter is used today, read-only.

**Video decode.** The MT6765's decoder is driven by MediaTek's proprietary firmware and user-space daemon; there is no open driver. A software decoder is the only option, and none is included:

- it cannot be a system component: the handset's 1 MiB catalog bank has about 20 KiB left for all packages together;
- it would be an open app's library, as Music's MP3 decoder is. Permissively licensed candidates are dav1d or its Rust port rav1d (AV1, BSD-2-Clause, with ARMv7 NEON code), libvpx (VP8/VP9, BSD-3-Clause), OpenH264 (H.264, BSD-2-Clause) and pl_mpeg (MPEG-1, MIT, one C file). Each needs its source vendored and, for the C ones, a C cross-build added to the open apps' build; none of that could be built or run while this change was written, and no speed on four Cortex-A53 cores has been measured;
- the display side would also need a YUV-to-BGRA conversion and scaling blit, which is not written (an app can already present a 720 x 1600 BGRA buffer it filled itself).
