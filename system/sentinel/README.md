# Sentinel

Component 26. The Open Runtime's policy decisions, in an address space of their own.

The Open Runtime (component 24) hosts every open app's memory and parses everything apps and the network hand it. Until this component existed it also decided what each app may do. Now it asks, and enforces the answer. Every input to a decision (where the program came from, its manifest text, the app's name, the path) is what the runtime tells the Sentinel, so this protects nothing against a compromised Open Runtime: it can ask with a lie, or not ask (see "What this does not do"). What the split does give: the consent store and the sealing key are outside the runtime's address space, the rules and the scorer's state are outside the process that parses hostile input, and every failure of the link is a refusal.

- **Capabilities.** May this app use the network, the microphone, the camera, Bluetooth, audio, Wi-Fi administration, the system commands ([decide.rs](decide.rs) `ask`)? The Sentinel reads the app's manifest text on every question.
- **Paths.** May this app reach this path, to read or to write, and with which error if not (`path_rule`)? Which capability a `/dev/violet` node or a `/dev/violet/sys` command needs (`device_cap`, `sys_cap`)? Does an `execve` cross into another app (`exec_crosses`)?
- **Consent.** The user's answers to prompts live here (`Grants`). The runtime gets them back only [sealed](seal.rs), writes that text to `/data/.grants`, and hands it back at start. Text this Sentinel's key did not seal is not loaded, and neither is a store older than the one already held.
- **The on-device scorer.** [scoring.rs](scoring.rs) runs the Shield's scorer ([runtime/open/scorer.rs](../../runtime/open/scorer.rs), built into this component and no longer into the Open Runtime). The runtime sends the telemetry it recorded; the Sentinel keeps the windows, scores them and says warn, quarantine or freeze. The runtime carries that out through its own Shield state ([guard.rs](../../runtime/open/guard.rs) `score_tick`): whether a program is actually contained is decided there (`shield.trip`, `eligible`), which the Sentinel's `enforced` byte only predicts. The runtime's side of the exchange (chunking, the reply's layout) is [common.rs](common.rs) `score_turn`, `score_head` and `score_results`, which the host tests run.
- **Sealed Shield state.** The Shield's saved mode (`/data/.shield-mode`) is sealed too.

## The edge

The supervisor ([supervisor.c](../supervisor/supervisor.c), "Sentinel") gives this process the receive side of one endpoint, 64 KiB of private heap, a request window it can only read and a reply window only it can write. It has no device, no storage, no network and no endpoint to any other service. Only the Open Runtime holds the calling side.

A request is a frame in the request window, announced by an IPC message with its sequence number, length and CRC-32 ([common.rs](common.rs)). [process.rs](process.rs) copies the frame out of the shared window before looking at it and passes it to [engine.rs](engine.rs). A frame that does not match what was announced, does not decode exactly, or carries a field the operation does not expect is answered `BAD!`.

The Open Runtime's side is [runtime/open/policy.rs](../../runtime/open/policy.rs) with [client.rs](client.rs). It fails closed: no answer, an answer to another question, a verdict word that is not one of the four, or output that does not match its CRC is a refusal (`Deny`, `EACCES`, "this command needs `system`", "this `execve` crosses apps"). A request too big for the window, or a path over 4 KiB, is refused without being sent (and without the once-a-boot `policy: no valid answer from the Sentinel` line). A manifest over 2 KiB is sent as no manifest: the minimal profile.

The supervisor refuses a whole catalog that has an Open Runtime and no Sentinel (one from before this component), so the boot falls back to the next catalog and in the end the factory's ([supervisor.c](../supervisor/supervisor.c) `parse`).

The Sentinel changes its consent store before it replies. If the reply is lost, the stub asks for the store as it stands (`OP_EXPORT`), so `/data/.grants` says what is enforced; with no answer at all it keeps the text it holds, which is the text it read at start until the Sentinel hands back a store, so a store that failed to load is never overwritten with an empty one.

If the Sentinel faults, the supervisor rebuilds the whole system, as for any component (and at the fifth fault before a healthy run it stops). The Sentinel alone is never restarted. The runtime's call in flight never returns, so nothing is granted in between; the new Sentinel holds no answers until the new runtime hands it the sealed store. Like every process the Sentinel also holds the send side of the supervisor's fault endpoint, which the kernel uses to report its faults; a message on it is taken as a fault (a rebuild), nothing more.

## The key

Sealing is encrypt-then-MAC built from HMAC-SHA-256 ([seal.rs](seal.rs)), with a separate key per use derived from one master key, `HMAC(secret, "violet sentinel seal v1")` (`seal::master`).

- **QEMU: the device root key.** The secret is the device root key ([tools/root_key.py](../../tools/root_key.py), the blob beside the disk that QEMU loads into one page). The supervisor maps that page into Storage and, read-only, into the Sentinel at `0x09320000`; never into the Open Runtime. No package, catalog or update carries it, so reading a system image (the inactive slot, an update passing through the runtime) gives nothing, a store sealed on one phone does not open on another, and a rebuild from another tree still opens what the phone sealed. With no valid blob (QEMU started without a disk) the Sentinel has no key: nothing is sealed, opened or loaded, answers hold for that start only.
- **Handset: a build secret, for now.** The handset has no device root key yet (no TEE, RPMB or fuse is used), so its Sentinel takes a 32-byte secret compiled into this package ([build.py](../../image/packages/build.py) `sentinel_key`): the file `VIOLET_SENTINEL_SEAL` names, which `VIOLET_RELEASE=1` requires; otherwise `sentinel-seal.bin` in `VIOLET_DEVELOPER_KEY_DIR` when that is set (shared by every tree, like the developer signing key), else `build/sentinel/seal-secret.bin`. Every phone built from the same file shares it, and whoever holds `sentinel.vpk` (the image, an update, a dump of the inactive slot through Storage's `SLOT` read) holds the key: on the handset the store protects against edits by something that does not have the image, nothing more. A different secret opens nothing the old one sealed; the runtime then logs `policy: .grants not opened` or `shield: .shield-mode not opened`.

## What this does not do

- **The Open Runtime is still the enforcement point, and it supplies every input.** A compromised runtime can skip the question, or tell the Sentinel a lie about who is asking: origin `Image` with the manifest `caps: system` gets `Allow` for any name, and nothing here tells that from a real image app. It can record a "yes" the user never gave (`OP_RECORD`: the consent prompt is drawn by the runtime) and have any Shield mode sealed (`OP_SEAL` takes the value it is given; only `Mode::at_boot`'s "stricter only" rule limits that). Giving the Sentinel inputs of its own (the image's manifest table from the supervisor or a measured boot record, the origin from the program's hash) is not done.
- **No freshness.** Sealing says a text came from this key, not when. The store's generation number is checked only against what the running Sentinel holds, and it starts at 0: after a restart an older store this key sealed (one from before the user said no) is accepted, and so is an older `.shield-mode`. Closing that needs a monotonic counter or storage only the Sentinel can write. On the handset, whose key is the build's, a store from another phone of the same build opens too.
- **The handset's key is not in hardware** (above).
- **The Shield's per-call rules stay in the Open Runtime** ([shield.rs](../../runtime/open/shield.rs) `evaluate`: the built-in rules, rate limits, quarantine and signed rules), and so does the companion link with its signature check ([services/sentinel](../../services/sentinel/mod.rs), which is a module of the Open Runtime despite its name). `/data/.settings` is not sealed.
- A manifest longer than 2 KiB is the minimal profile (its comments count: nothing strips them); an owner longer than 64 bytes is refused by the Sentinel.
- A hung Sentinel hangs the Open Runtime's call: nothing is granted, and nothing restarts the Sentinel. When an open app is in front, the supervisor's stall check then stops the Open Runtime as it does for any stall of it.
- Containment of a faulting Sentinel on its own (A1-sentinel-contain) is not done: its fault rebuilds everything.

## Tests

`make test-unit` runs [tests/sentinel_host.rs](tests/sentinel_host.rs) (seconds): the shipped stub joined to the shipped engine in memory ([hostlink.rs](hostlink.rs)). It checks that asking gives exactly what the decisions say, that every single-bit change to a request is refused, that a silent or lying Sentinel grants nothing, the sealing, the master key from a root key blob (against tools/root_key.py's format and Python's HMAC) and that another phone's store does not open, an unkeyed Sentinel, the consent store across a restart and after a lost reply, oversized requests, the runtime's side of a scorer turn as shipped (100-record chunks, reply decoding), and that the scorer here decides what the scorer beside the policy did. The decisions themselves are tested in [runtime/open/tests/policy_host.rs](../../runtime/open/tests/policy_host.rs).

For a guest test, an image built with `VIOLET_SENTINEL_FAULT=1` has an Open Runtime that changes one bit of its own request, after summing it, whenever the request is about a path ending in `sentinel-fault-probe`: opening `/tmp/sentinel-fault-probe` must then fail with `EACCES` while any other `/tmp` file opens, and the log says `policy: no valid answer from the Sentinel`. Normal images carry none of that code.

The process itself (`process.rs`, the supervisor's wiring, the root key page) has been type-checked for the target but not yet run in an image. Sizes, measured with the image build's flags: the Open Runtime's package went from 419,184 to 415,096 bytes in QEMU and from 423,284 to 419,196 on the handset; the Sentinel's package was 32,888 bytes. The review fixes (lost-reply recovery, the scorer exchange in common.rs, size pre-checks, two log lines) left the Open Runtime's code 45 bytes smaller in QEMU and 5 bytes smaller on the handset (rustc objects, same flags).
