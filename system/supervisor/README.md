# Process supervisor

The [shared Moto and QEMU first task](supervisor.c) constructs address spaces, threads and endpoint permissions. It starts the launcher, Runtime and services, opens apps on demand, and reinitializes private execution state on Quit. Each Runtime worker can contact its assigned service. Only Display and the Open Runtime hold the scanout mapping; the Open Runtime draws only while Runtime has given it the screen.

The supervisor receives kernel fault messages and monitors in-flight service calls. Runtime and the foreground app also have progress deadlines. After a fault or a 20-second stall it restarts the managed group. A guest-installed catalog that fails during its trial (from its commit until it has run healthy for 20 seconds) is retired on disk and the previous catalog runs; one that has passed its trial, or was found at power-on, is restarted as it is, so a crash cannot bring back older packages ([details](../package-manager/README.md#signatures-and-versions)). On QEMU a host-staged catalog falls back to the previous staged one at any time. Repeated failures during startup stop the recovery loop.

The Open Runtime is handled on its own, so that a fault in it never restarts the services. A fault message from it (a panic, a bad pointer) starts its thread again at the package entry on a fresh stack, with its memory as the fault left it; the runtime then closes the one app it was serving and carries on ([runtime/open/contain.rs](../../runtime/open/contain.rs)). [open_recover.h](open_recover.h) allows three such restarts in a row, counts afresh after ten seconds without a fault, and allows at most eight per boot however the faults are paced ([test_open_recover.c](test_open_recover.c), in `make test-unit`). A fault the runtime cannot pin on one app, or one during its boot, makes it suspend its own thread. Past that, or when the Open Runtime stalls without faulting, its thread is suspended and the fault recorded, as before: open apps stop until the phone restarts, the services keep running. A just-installed catalog still rolls back.

[procmgr.rs](procmgr.rs) and [frames.rs](frames.rs) in this folder are the open apps' process manager. Despite where they live, they are compiled into the Open Runtime, not into the supervisor: see [the Open Runtime](../../runtime/open/README.md), "Which app holds which page" and "Not done yet".

Before it runs any package the supervisor checks the package's publisher signature against the keys pinned in the boot image, and its security version against the version floors ([signatures and versions](../package-manager/README.md#signatures-and-versions)). A catalog with a package that fails either check is not booted.

The [Sentinel](../sentinel/README.md) gets one endpoint that only the Open Runtime can call, a private heap and two shared windows (requests it can only read, replies only it can write), and nothing else. A catalog without a Sentinel does not start the Open Runtime, and the Sentinel cannot be removed while the Open Runtime is installed. A Sentinel fault rebuilds the system like any other.

## The timekeeper

The supervisor also runs the system's one timer thread ([timekeeper_thread.h](timekeeper_thread.h); the decisions are in [platform/sel4/include/timekeeper.h](../../platform/sel4/include/timekeeper.h) and tested on the host by [tests/timekeeper_test.c](tests/timekeeper_test.c)). It owns the nonsecure physical timer, the only timer user mode can program on both boards, and wakes every process that sleeps, so a delay blocks in the kernel instead of spinning on yields and the CPU can idle. The supervisor's own loop blocks too: it waits on its lifecycle endpoint and is woken every 100 ms for the health checks.

- Each process shares one page with the timekeeper, holds a notification to wait on and a send-only capability to kick the timekeeper with (slots 29 and 30; the kick is badged with the process's own bit, so the timekeeper knows who asked). The pages are separate frames: a process can ask only for its own wake-ups. The deadline itself is kept by the timekeeper.
- The thread runs above everything (priority 255) and never blocks except to wait. It has no IPC buffer and makes only register-only system calls, because the supervisor's two threads would otherwise share one.
- A process is told the timekeeper serves it by its second start argument. If the timer does not fire at start-up, if a process could not be given its page (memory or capability slots short), or with `VIOLET_TIMEKEEPER=0`, that process is started without it and keeps the old yield loop; the Open Runtime then gets the timer interrupt itself, as before.
- The Open Runtime's timer is served by the same thread: its deadlines arrive on the notification and with the badge its interrupt had. If the Open Runtime cannot be attached, the whole timekeeper stops before any other process is, so the Open Runtime can take the interrupt itself. The Sentinel is never attached (it never sleeps and holds only its endpoint and windows).
- The kernel lets every user thread program this timer, open apps included. A guard thread (priority 100, with every process and app thread) kicks the timekeeper whenever the timer is more than 2 ms overdue, so an app that stops or moves the timer delays sleepers by up to a time slice instead of hanging them and the health checks; it waits in WFI when nothing else runs. No guard, no timekeeper. If WFI traps at user level, the guard is restarted yielding only after three health checks ([services/power](../../services/power/README.md#idle)). Only a kernel change that exports the timer to the supervisor's threads alone removes the exposure.
- Power may freeze the timekeeper for a suspend to idle ([services/power](../../services/power/README.md#suspend-to-idle)); no other process's page is obeyed for that.

None of the kernel side has run yet: it was written and compiled for both boards without an image build, and is unverified until one boots. The handset has never run it. With MCS (`VIOLET_MCS=1`) it has not even been compiled.
