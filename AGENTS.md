# Notes for coding agents

Start with [README.md](README.md): how to build, run and test, the architecture, and where to change the code.

- **Keep CI under 5 minutes.** CI runs only `make test-unit` and `make test-ci` (two QEMU tests). Don't add QEMU suites to `test-ci` or new jobs to `.github/workflows/ci.yml`. If CI must cover something, extend an existing test or add a host test that takes seconds. Leave apps CI doesn't need out of its build (`VIOLET_OPEN_SKIP`).
- **Keep the local loop under 10 minutes.** `make test-local` is the loop: `test-unit`, `test-system` (the AArch64 end-to-end test), `test-ci` (on the AArch64 image) and `test-system32` (the 32-bit end-to-end test, two boots); 261 s measured as one command (November 28, 2026). Run it before pushing.
- **AArch64 is the default architecture.** `make moto`, `make qemu-image`, `make emulator` and the tests above use it; `moto32`, `qemu32-image`, `emulator32` and `test-system32` are the 32-bit system, which the suites that only it carries (isolation probes, audio, test-open, memory, packages, agent, Shield, `test-moto-*`) use.
- **Test with a host integration test, not a new QEMU suite.** Add a few lines to [tests/integration](tests/integration/README.md): each test builds its own phone in memory from the shipped sources, so tests run in parallel in milliseconds and in CI. Keep new logic callable from the host: put hardware and kernel access behind a narrow function or trait so the framework can fake only that edge. Only what needs the real kernel, page tables or boot path goes to QEMU, into [targets/qemu/test_system.py](targets/qemu/test_system.py) within its boots. Do not add `targets/qemu/test_*.py` scripts or `make test-*` targets. [docs/test-map.md](docs/test-map.md) records where each old QEMU assertion went.
- Rust is the preferred language for new VioletOS code.
- Handset work: `make moto` (AArch64), then `services/usb-diagnostics/host/moto-flash build/sel4/moto-aarch64/boot.img`. `build/moto-package` talks to the phone over USB. The running 64-bit system marks slot B successful; moto-flash clears that mark (`set_active a`, `set_active b`) so a new image is a counted trial.
