# Storage service

Storage keeps two things for apps. The built-in apps (the SDK's) each get a private flat directory selected from the kernel-assigned identity, described first. The open apps' `/data` is a filesystem of its own, [described below](#data-the-filesystem-server). For the first: The [SDK](../../runtime/sdk.rs) can list, read, write, truncate and delete named files. Each directory holds four files of up to 4 KiB each, except the open apps' shared one, which holds 32 (the extra 28 sit after every directory's first four, in sectors 608–1112). The [file store](files.rs) writes data into an inactive bank and flushes it before committing a checksummed directory entry. Private checkpoint values retain their original two-sector disk format.

**Replacing a file whole.** A message carries 24 bytes, and a plain `FILE_WRITE` is a commit of its own, so a file changed that way passes through part-new states that a power cut can leave behind. With `FILE_STAGED` in `arg` the pieces collect in the inactive bank instead, unseen, and the closing `FILE_TRUNCATE` publishes the file in one commit: eight sector writes and two flushes for 4 KiB, where it used to be a full rewrite and two flushes per 24 bytes. Each owner has one replacement in progress at a time and cannot disturb another owner's. The disk format is unchanged, so an older image reads the same volume. Still true: four files of 4 KiB with 16-character names and no directories; an app using the SDK's plain writes is atomic only per 24 bytes. The open apps' 32 slots of this store are no longer written: they are read once, to move their files into `/data`'s filesystem (below), and left as they were.

## /data: the filesystem server

The open apps' `/data` is VioletFS ([violetfs/](violetfs/mod.rs), below) mounted by Storage on a data volume and served by path. The 32 files of 4 KiB with 16-character names are gone: `/data` has folders, names of up to 255 bytes and files as large as the volume and the phone's memory allow (the Open Runtime works on a file in memory, see its side below).

- **The volume** ([volume.rs](volume.rs), [extent.rs](extent.rs)). The disk driver names one extent of sectors: in QEMU the 2 MiB after the installed apps (sectors 28672 to 32768 of the 16 MiB disk); on a handset whose userdata VioletOS has claimed, the second gibibyte of it (the installed apps keep the first, which is more than the app store can reach); otherwise the 464 KiB at the end of Storage's first megabyte that the flat files never used. **Where it is is decided once** ([mount.rs](mount.rs), `extent::decide`): before the first format Storage records the place in two sectors of the first megabyte (1122 and 1123), and marks the record done once the old files are in. From then on `/data` is served from that place only. A boot that cannot reach it (the read of the userdata claim failed, a QEMU disk made smaller) serves nothing: ENODEV, so the phone stays locked and nothing is written, instead of serving the small volume with an older passcode and revoked grants back. A volume made in the first megabyte stays there after userdata is claimed (moving `/data` to the larger extent is not done). A volume that is gone after its record is done (header and superblocks lost) is `DATA LOST`: it is never formatted again and the old files are never copied in again. A disk that is there but has no room for a volume (under a megabyte) or whose record cannot be read answers ENODEV too; only a missing disk answers OFFLINE, which the runtime takes as "nothing was ever kept". Losing both record copies together with the volume's header and superblocks brings back the first-boot path. Its first 4 KiB is a header written once the filesystem has been made. No header and nothing that mounts: the filesystem is made (a `format` that was cut short is done again). A header and a filesystem that does not mount: nothing is formatted and `/data` is unavailable (Storage's diagnostic says `DATA MOUNT`), because under a cipher a wrong key looks like an empty disk and must not erase the files. The filesystem sits on `crypt::open(dev, &volume_key)`; today that is a pass-through in volume.rs, so **the volume is not encrypted** (the cipher of [crypt/](crypt/mod.rs) is not wired in; the header names the cipher, so a build that is will refuse a volume made without one instead of misreading it).
- **The server** ([vfs.rs](vfs.rs), requests in [vfsproto.rs](vfsproto.rs)). The Open Runtime sends a request through the 64 KiB window it shares with Storage (an `APPSTORE` message with bit 29 in `value`; Runtime forwards these for the Open Runtime only, Storage takes them from Runtime only): list, read, replace a file whole (`PUT`, pieces that show nothing until the last one), make a folder, remove, commit, and also stat, write in place, truncate, rename, chmod, statfs and set a quota. Paths are walked in Storage; `.` and `..`, empty parts, parts over 255 bytes and the server's own folder `/.vfs` are refused.
- **Owners and permissions.** The owner of a file follows from the first part of its path, as the runtime's policy has it ([policy.rs](../../runtime/open/policy.rs) `owns_data`): the app `NAME` owns `/data/NAME` (a file, or a folder and everything in it) and `/data/NAME.ANYTHING`; names that start with a dot are the system's. Every inode carries its owner's number and its mode. A request made for an app (`who`) is held to that rule a second time in Storage (another owner's names and the dot names answer ENOENT unless the runtime says its policy shares the name) and to the owner's mode bits (read 0400, write 0200, and write on a folder to add or remove names in it). **What this is today:** the requests the Open Runtime sends are its own write-back and carry no `who`, so on a running phone the rule that holds apps apart is still the runtime's (`path_rule`, at every path an app names); Storage's check is tested on the host and waits for the runtime to make app requests in the app's name. Storage has one client, so `who` is the runtime's word in any case: it guards against the runtime's mistakes, not against the runtime.
- **Quota.** Blocks and files are counted per owner by VioletFS and checked before anything changes. An app owner may hold a quarter of the volume's blocks and a quarter of its files (EDQUOT beyond; `QUOTA` sets other limits), and no app can write once the free blocks are down to the system's reserve of a sixteenth (ENOSPC), so that settings can still be saved on a full volume. The system's names are the dot names and `networks` and `relay` (saved Wi-Fi networks and the Phone Internet choice, which the runtime keeps for Settings); `/data/agent` is the agent app's own. A replacement (`PUT`) collects as the system's and is charged to the owner only for what it adds to the file it replaces (each piece checks it, and VioletFS's `chown_over` checks it again in the step before the rename), so a file can be rewritten up to the whole share, not half of it; the room it needs on the volume is still the old and the new copy together until the last piece. At most 120 owners hold something at one time; an owner that holds nothing gives its number back. The runtime writes back after the app's `write` returned, so **an app sees EDQUOT and ENOSPC from `fsync`, `fdatasync` and `sync`**, not from `write`; a file that does not fit stays in memory, is tried again, and is not there after a restart. `statfs` in the runtime does not report the volume yet.
- **The old files move once.** The first time a volume is made (the record above is not done yet), the 32 slots are copied into the top of `/data` under their names (so saved Wi-Fi networks, settings, grants and the passcode record come along) and `/.vfs/migrated` is made in the transaction that ends the copy. Nothing is served before that marker is durable, and a copy that was cut short is done again from the slots, which are never written: after any power cut the volume shows every old file or is not available yet. A slot that cannot be read, or one whose name the old store could not have made (`.`, `..`, `.vfs`), stops the move (`DATA MIGRATE`) and `/data` stays unavailable, which keeps the phone locked rather than starting without a passcode record that may be there. Each slot is read in one go ([legacy.rs](legacy.rs): its two bank headers and its pages, at most 10 sectors), so 32 full slots are at most 320 sector reads, a couple of seconds at the handset's 100 KiB/s; the move runs before Storage answers anyone. The slots are left as they were: an older system image in the other boot slot still reads them, they are not kept up to date, and what they hold (Wi-Fi keys among it) is still on the disk in the clear.
- **After a device error** the filesystem stops; Storage mounts it again before the next request, which brings back the last committed state, and answers ESTALE (each mount has a number) so that the client knows what it sent since may be gone.

**The Open Runtime's side** is [writeback.rs](writeback.rs), run by [data.rs](../../runtime/open/data.rs): it loads `/data` at start and decides what is sent when; the host tests drive it, and the runtime's own [fs.rs](../../runtime/open/fs.rs), against the server.

- At start every folder and file of the volume is read into memory, each file into a buffer of its size allocated once (no regrowth). A file there is no memory for is left on the volume, unseen this run, if it is an app's; if it is the system's (a dot name) the load fails. If the load fails part way, nothing is written back for the rest of the run (the volume is not written over with less than it has) and the phone stays locked.
- A changed file is sent whole as one replacement, a piece of 8 KiB per pass of the runtime's loop, so a save does not hold the runtime; until the last piece the volume shows the old file. The pieces are read from the file as it is (no copy is made to send it); a file written to meanwhile starts over. A commit follows when nothing is left to send (or 64 passes after the first change not yet committed): only then does the change survive a power cut.
- Files and folders to write go before names to remove: a rename is the new name, then the old one gone, and a cut can leave both names but not neither. The name a rename took a file from (fs.rs `moved`) is not removed while any save is failing, whatever the reason (EDQUOT and ENOSPC included); a plain removal is never held back, since it may be what makes room.
- A save that fails with an error is tried again after 32 passes, then 64, up to 512. One that found the volume or the quota full is not sent again on a timer, only when a removal has made room, the file changed size, or a `sync`/`fsync` asks. What the volume then holds for that name counts as unknown: the file is sent again even if it goes back to its old contents.
- `fsync` and `fdatasync` write back the file (or everything under the folder) of their descriptor and commit before they return, and `sync` everything. They return `EIO` when Storage failed (or `/data` could not be loaded), `ENOSPC` and `EDQUOT` as above. One call sends at most 128 requests (a megabyte) and returns `EINTR` if that was not enough. Each app may send 256 requests in a burst and one more every 8 ms: the call that goes over is answered late, and further calls get `EINTR` without any work until the app is back within its allowance. That bounds how much of the runtime's time, and how many flash writes, one app's syncs can take.
- When Storage answers ESTALE (it had to mount the volume again), nothing more is written until the restart and `sync` says `EIO`, as when the disk is lost.
- Not done: files are whole in memory, so a file cannot be larger than memory allows, everything in `/data` is read at start, and a file of a megabyte is sent whole when a byte of it changes. `mmap` with `MAP_SHARED` is not written back. Modes are not kept (every file comes back 0644). File times are kept, a renamed file's included; a folder's time is that of the last request that carried one. One file is at most 16 MiB (the runtime's write bound, [vma.rs](../../runtime/open/vma.rs) `resize_file`), and the whole of `/data` must fit in the runtime's memory again at the next start (the per-app quota on a claimed handset's volume is larger than that memory). A name under `/data` longer than 255 bytes, or a path longer than 1024, is refused when it is made.

`make test-open-apps` checks that an open app's `/data` file survives a VM restart (not run again since `/data` moved to the filesystem server: the image was not built in the change that made it). System package updates use a separate boot-accessible volume, so the supervisor can recover the storage service itself.

**Installed apps.** The Open Runtime keeps programs installed by the agent in an extent of their own (the last 12 MiB of boot_b on the handset, beyond the flashed image, or the first gibibyte of userdata once VioletOS has claimed it, where `/data`'s volume follows; sectors 4096 onward in QEMU). Storage only reads and writes its sectors, up to 128 at a time, through a 64 KiB window shared with the Open Runtime (`APPSTORE` in [protocol.rs](../../runtime/protocol.rs)); the format is in [appstore.rs](../../runtime/open/appstore.rs).

**Boot slots (full-system updates).** [slotwrite.rs](slotwrite.rs) writes a system update into the *inactive* boot slot through the same window (an `APPSTORE` request whose sector has bit 31 set), for the Open Runtime only; it can never address the running slot or anything else. The first image write of an update makes that slot unbootable in the A/B metadata (Android's `bootloader_control`, [slot.rs](../../targets/moto-g-pure/slot.rs)) and flushes before any image byte changes; the manifest is held in memory until the switch, so a refused bundle changes nothing on the disk. Nothing is written or switched while the running slot is not yet marked successful (the inactive slot is then the only fallback), and a switch always makes the slot unbootable before it activates it, so it is a counted trial even if it was proven before. Storage then reads the image back from the disk and hashes it (its own SHA-256, [sha256.rs](sha256.rs)), in order from sector 0, up to 2048 sectors per request. Only the supervisor (badge 0) can read the manifest, take that digest, switch slots (and only to a digest that is still current and equals the one it checked) and mark the running slot successful. In QEMU the slots exist on a data disk of at least 145 MiB (misc at 16 MiB, two 64 MiB slots after it; `make test-ota` makes one); on the normal 16 MiB disk updates are unavailable. On the handset this is built only with `--cfg slot_ota`, which no build sets ([emmc.rs](../../targets/moto-g-pure/emmc.rs)). Host tests: [tests/slotwrite_host.rs](tests/slotwrite_host.rs), in `make test-unit`.

**VioletFS** ([violetfs/](violetfs/mod.rs)) is the filesystem under `/data`: directories, names of up to 255 bytes, hard links, files to 4 TiB through block pointers, a mode and an owner per inode, and a quota of blocks and files per owner, counted and checked in the filesystem (who is charged for what is below). Storage mounts it on the data volume (above); hard links and symbolic links are in the filesystem and not offered by the server.

- *Consistency.* Metadata changes go to a journal, are committed by one checksummed record, and are copied into place afterwards; file data is written to blocks that were free at the last commit and flushed before the record that points at it. Each operation is all-or-nothing, a rename included; several share a transaction until `commit`. What is all-or-nothing in a write is the blocks it touches: up to `atomic_write()` bytes (256 KiB on a volume over 36 MiB, less on a smaller one) from a block boundary, `atomic_write_at(offset)` bytes from anywhere else. A longer write, the freeing of a large file and the giving back of a directory's empty blocks span transactions: a cut leaves a prefix of the write, and `mount` finishes the other two. A journal record that `mount` does not accept is zeroed before the volume is used, so a transaction that was rolled back cannot be replayed after a later cut. Metadata blocks carry a CRC-32; a block that fails it, or a device error, on any call (reads too) stops the filesystem until the next mount. File data has no checksum and nothing is repaired.
- *Directories.* `readdir` does not trust its cookie: it walks the block's records and answers `Invalid` for a cookie that is not the start of one, so bytes of a name are never read as an entry. Removing names gives back the empty blocks at the end of a directory; blocks before the last name stay (no compaction).
- *Quota.* An owner has a row in a table of 128 only while it holds something or has a limit; a refused operation takes none. A directory's blocks are charged to the directory's owner whoever adds the names, and a hard link costs the linker nothing, so an owner who may write in another's directory can use up that owner's block quota with names until they are removed. The caller has to decide who may add names where; a limit on links per owner is not here.
- *No heap.* One `Fs` value of about 45 KiB (eight cached blocks, the journal record, two scratch blocks) over the [`BlockDev`](blockdev.rs) trait; about 32 KiB of code for ARM. It does not fit Storage's 32 KiB stack: the server keeps it in a static (52 KiB of the Storage package with the server's own state; the package grew from 24 KiB to 122 KiB with the filesystem).
- *Wear.* Allocation continues from where it last stopped and goes round the volume, and `discard_free` reports free blocks to the device (nothing calls it yet, and neither disk driver passes a discard on). The journal and the state block stay where they are and are rewritten at every commit; spreading those writes is left to the eMMC's own wear levelling. There is no wear counting and no bad-block handling here.
- *Left to the caller:* paths and permission checks (vfs.rs does both), open files that outlive their name, and a clock (the runtime sends each file's time). `format` is not atomic. The check (`check`) needs a bit per block and a counter per inode from the caller.

**Encryption at rest** ([crypt/](crypt/mod.rs), [docs/encryption-at-rest.md](../../docs/encryption-at-rest.md)). `crypt::open(dev, &volume_key)` is a `BlockDev` that encrypts every sector below it with XTS-AES-256 (constant time, no tables) and keeps a key block in its first 4 KiB: the volume key wrapped under the device root key and the lock screen's passcode secret, with the count of wrong attempts saved before each one is checked. Changing the passcode rewraps the key and rewrites no data. Its host tests ([crypt/tests/host.rs](crypt/tests/host.rs), in `make test-unit`) check published cipher vectors and mount VioletFS on it through power cuts. Not in use yet: Storage does not mount through it, the installed apps' extent does not go through `crypt::open_extent`, the lock screen does not feed it, QEMU's root key is a stand-in blob loaded at boot ([tools/root_key.py](../../tools/root_key.py)), and the handset has no root key at all, so nothing on a running image is encrypted today. XTS gives confidentiality only: there is no integrity or anti-rollback for `/data` or the app store (an older ciphertext can be put back).

**Tests.** `make test-unit` builds [tests/host.rs](tests/host.rs) on the host: the service's sources unchanged over a [disk that can lose power](tests/testdisk.rs). The disk logs every write and flush; the sweep then rebuilds what the medium could hold after a cut at each of them (nothing since the last flush, everything issued, the write in flight torn within a sector, random subsets of the unflushed sectors, and at each flush every unflushed write dropped or kept alone) and for a sample a second cut during recovery. Every image must mount, pass the full check, hold exactly the state of the last durable commit or of the one in flight, and take new writes. One test cuts twice with work in between: a cut, a mount, another transaction in the same journal slots and a cut at each of its writes (this found a rolled-back transaction being replayed). The same sweep runs over the staged replacement of files.rs, over the server ([vfs_tests.rs](tests/vfs_tests.rs): making the volume, the move of the old files written by the real files.rs, a replaced file, a rename; with the permission and quota rules, the full owner table, the smallest volume with all 32 slots full, and a device error) and over the Open Runtime's own saves, renames, removals and folders sent through the real server ([writeback_tests.rs](tests/writeback_tests.rs), which also fails Storage's replies, exceeds a quota and checks what `sync` reports; [fs_tests.rs](tests/fs_tests.rs) puts the runtime's fs.rs on top), and over Storage's own mount.rs with its disk adapter on a stand-in driver ([mount_tests.rs](tests/mount_tests.rs): where the volume is placed and held, userdata that comes and goes, a lost volume, a disk with no room, a cut during the first boot, and the old slots read against files.rs). It is shown to fail when a flush is left out of VioletFS, when freed blocks are reused early, and for the old 24-bytes-at-a-time save. Other tests compare random operations with an in-memory model, fail the device at every operation, damage metadata, fill the volume and exceed quotas. `make test-storage-long` runs more of the same (local, under a minute). The cut model is a model: whether the handset's eMMC honours a cache flush or can tear a sector is only found on the handset, and no test here runs in QEMU or on the phone.
