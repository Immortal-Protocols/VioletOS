# Storage service

Each app gets a private directory selected from its kernel-assigned identity. The [SDK](../../runtime/sdk.rs) can list, read, write, truncate and delete named files. Each directory holds four files of up to 4 KiB each, except the open apps' shared one, which holds 32 (the extra 28 sit after every directory's first four, in sectors 608–1112). The [file store](files.rs) writes data into an inactive bank and flushes it before committing a checksummed directory entry. Private checkpoint values retain their original two-sector disk format.

**Replacing a file whole.** A message carries 24 bytes, and a plain `FILE_WRITE` is a commit of its own, so a file changed that way passes through part-new states that a power cut can leave behind. With `FILE_STAGED` in `arg` the pieces collect in the inactive bank instead, unseen, and the closing `FILE_TRUNCATE` publishes the file in one commit: eight sector writes and two flushes for 4 KiB, where it used to be a full rewrite and two flushes per 24 bytes. Each owner has one replacement in progress at a time and cannot disturb another owner's. The disk format is unchanged, so an older image reads the same volume. Still true: 32 files of 4 KiB with 16-character names for open apps and no directories; native apps using the SDK's plain writes are atomic only per 24 bytes.

**The Open Runtime's side** is [writeback.rs](writeback.rs), run by [data.rs](../../runtime/open/data.rs): it decides what is sent when, and the host tests drive it against files.rs.

- A changed `/data` file is sent as one staged replacement, 16 messages per pass of the runtime's loop (a 4 KiB file is 172 messages, 11 passes: 50 to 180 ms while an app runs, about half a second with none running), so a save does not hold the runtime. Until the last message Storage shows the old file.
- Files to write go before files to delete: a rename is two commits, the new name first, and a cut can leave both names but not neither. A delete is not sent while a save that failed is still being retried (five tries, then it goes). One exception: when all 32 slots are taken the new name cannot be stored first, so the old name's delete goes first and the new name follows in the same pass; a cut between the two loses the file.
- A save that fails stays queued and is tried again after 32 passes, then 64, up to 512. What Storage then holds for that name counts as unknown: it is rewritten even if the file goes back to its old contents, and a delete is always sent.
- `fsync` and `fdatasync` write back the file (or everything under the directory) of their descriptor before they return, and `sync` everything. They return `EIO` when Storage failed, `ENOSPC` when the 32 slots are taken, and for a file asked about by its own descriptor `EFBIG` over 4 KiB and `EINVAL` for a name `/data` does not keep (asked about the directory or everything, such files do not count). One call sends at most 400 messages and returns `EINTR` if that was not enough. Each app may send 1024 messages in a burst and one more every 4 ms: the call that goes over is answered late, and further calls get `EINTR` without any work until the app is back within its allowance. That bounds how much of the runtime's time, and how many flash writes, one app's syncs can take.
- Not changed: a file over 4 KiB or with a name Storage does not keep is not stored at all, and an older version of a file that grew past 4 KiB stays in Storage and comes back after a restart (`fsync` on it says `EFBIG`). All open apps share the 32 slots, so one app can fill them for the others.

`make test-open-apps` checks that an open app's `/data` file survives a VM restart. System package updates use a separate boot-accessible volume, so the supervisor can recover the storage service itself.

**Installed apps.** The Open Runtime keeps programs installed by the agent in an extent of their own (the last 12 MiB of boot_b on the handset, beyond the flashed image; sectors 4096 onward in QEMU). Storage only reads and writes its sectors, up to 128 at a time, through a 64 KiB window shared with the Open Runtime (`APPSTORE` in [protocol.rs](../../runtime/protocol.rs)); the format is in [appstore.rs](../../runtime/open/appstore.rs).

**Boot slots (full-system updates).** [slotwrite.rs](slotwrite.rs) writes a system update into the *inactive* boot slot through the same window (an `APPSTORE` request whose sector has bit 31 set), for the Open Runtime only; it can never address the running slot or anything else. The first image write of an update makes that slot unbootable in the A/B metadata (Android's `bootloader_control`, [slot.rs](../../targets/moto-g-pure/slot.rs)) and flushes before any image byte changes; the manifest is held in memory until the switch, so a refused bundle changes nothing on the disk. Nothing is written or switched while the running slot is not yet marked successful (the inactive slot is then the only fallback), and a switch always makes the slot unbootable before it activates it, so it is a counted trial even if it was proven before. Storage then reads the image back from the disk and hashes it (its own SHA-256, [sha256.rs](sha256.rs)), in order from sector 0, up to 2048 sectors per request. Only the supervisor (badge 0) can read the manifest, take that digest, switch slots (and only to a digest that is still current and equals the one it checked) and mark the running slot successful. In QEMU the slots exist on a data disk of at least 145 MiB (misc at 16 MiB, two 64 MiB slots after it; `make test-ota` makes one); on the normal 16 MiB disk updates are unavailable. On the handset this is built only with `--cfg slot_ota`, which no build sets ([emmc.rs](../../targets/moto-g-pure/emmc.rs)). Host tests: [tests/slotwrite_host.rs](tests/slotwrite_host.rs), in `make test-unit`.

**VioletFS** ([violetfs/](violetfs/mod.rs)) is the filesystem meant to replace the fixed slots: directories, names of up to 255 bytes, hard links, files to 4 TiB through block pointers, a mode and an owner per inode, and a quota of blocks and files per owner, counted and checked in the filesystem (who is charged for what is below). It is not in use yet: nothing mounts it, Storage is not built with it, and the Open Runtime's files are unchanged. This wave lands the code and its tests.

- *Consistency.* Metadata changes go to a journal, are committed by one checksummed record, and are copied into place afterwards; file data is written to blocks that were free at the last commit and flushed before the record that points at it. Each operation is all-or-nothing, a rename included; several share a transaction until `commit`. What is all-or-nothing in a write is the blocks it touches: up to `atomic_write()` bytes (256 KiB on a volume over 36 MiB, less on a smaller one) from a block boundary, `atomic_write_at(offset)` bytes from anywhere else. A longer write, the freeing of a large file and the giving back of a directory's empty blocks span transactions: a cut leaves a prefix of the write, and `mount` finishes the other two. A journal record that `mount` does not accept is zeroed before the volume is used, so a transaction that was rolled back cannot be replayed after a later cut. Metadata blocks carry a CRC-32; a block that fails it, or a device error, on any call (reads too) stops the filesystem until the next mount. File data has no checksum and nothing is repaired.
- *Directories.* `readdir` does not trust its cookie: it walks the block's records and answers `Invalid` for a cookie that is not the start of one, so bytes of a name are never read as an entry. Removing names gives back the empty blocks at the end of a directory; blocks before the last name stay (no compaction).
- *Quota.* An owner has a row in a table of 128 only while it holds something or has a limit; a refused operation takes none. A directory's blocks are charged to the directory's owner whoever adds the names, and a hard link costs the linker nothing, so an owner who may write in another's directory can use up that owner's block quota with names until they are removed. The caller has to decide who may add names where; a limit on links per owner is not here.
- *No heap.* One `Fs` value of about 45 KiB (eight cached blocks, the journal record, two scratch blocks) over the [`BlockDev`](blockdev.rs) trait; about 32 KiB of code for ARM. It does not fit Storage's 32 KiB stack: keep it in a static.
- *Wear.* Allocation continues from where it last stopped and goes round the volume, and `discard_free` reports free blocks to the device. The journal and the state block stay where they are and are rewritten at every commit; spreading those writes is left to the eMMC's own wear levelling. There is no wear counting and no bad-block handling here.
- *Left to the caller:* paths, permission checks (the mode and owner are stored, not enforced), open files that outlive their name, and a clock. `format` is not atomic. The check (`check`) needs a bit per block and a counter per inode from the caller.

**Tests.** `make test-unit` builds [tests/host.rs](tests/host.rs) on the host: the service's sources unchanged over a [disk that can lose power](tests/testdisk.rs). The disk logs every write and flush; the sweep then rebuilds what the medium could hold after a cut at each of them (nothing since the last flush, everything issued, the write in flight torn within a sector, random subsets of the unflushed sectors, and at each flush every unflushed write dropped or kept alone) and for a sample a second cut during recovery. Every image must mount, pass the full check, hold exactly the state of the last durable commit or of the one in flight, and take new writes. One test cuts twice with work in between: a cut, a mount, another transaction in the same journal slots and a cut at each of its writes (this found a rolled-back transaction being replayed). The same sweep runs over the staged replacement of files.rs and over the Open Runtime's own saves, renames and deletes ([writeback_tests.rs](tests/writeback_tests.rs), which also fails Storage's replies, fills the 32 slots and checks what `sync` reports), and it is shown to fail when a flush is left out of VioletFS, when freed blocks are reused early, and for the old 24-bytes-at-a-time save. Other tests compare random operations with an in-memory model, fail the device at every operation, damage metadata, fill the volume and exceed quotas. `make test-storage-long` runs more of the same (local, under a minute). The cut model is a model: whether the handset's eMMC honours a cache flush or can tear a sector is only found on the handset, and no test here runs in QEMU or on the phone.
